# 설계 원칙

하네스를 만들 때 판단 기준으로 쓰는 문서다. 근거가 된 레퍼런스는 [references.md](references.md)에 있다.

## 하네스란

하네스는 에이전트에서 모델을 뺀 나머지 전부다. 다음이 모두 하네스에 포함된다.
- 에이전트가 읽는 지침
- 에이전트가 쓰는 도구
- 결과를 확인하는 수단
- 행동을 막는 장치
- 세션 사이에 남기는 상태

이 저장소는 그중 iOS 프로젝트에 맞춰 우리가 직접 구성할 수 있는 부분을 만든다.

## 계층

| 계층 | 하는 일 | 예 |
|---|---|---|
| Context (가이드) | 에이전트가 행동하기 전에 알려준다 | AGENTS.md, 경로 규칙, 스킬 |
| Execution (실행 도구) | 에이전트가 일을 하는 손이다 | 빌드·테스트 실행 래퍼, 시뮬레이터 조작 |
| Validation (센서) | 결과가 맞는지 판정한다 | 컴파일러, 테스트, 린트, 코드 리뷰 |
| Enforcement (강제) | 모델 판단과 상관없이 막는다 | 훅, 권한 deny |
| State (설정·상태) | 위 계층이 함께 쓰는 데이터 | 프로젝트 설정 파일, 실행 계획, 실패 기록 |

Validation은 두 종류가 있다.

- **결정적 검증**: 컴파일러, 테스트, 린트처럼 같은 입력이면 항상 같은 결과를 낸다.
  - 빠르고 싸고 믿을 수 있어서 변경할 때마다 돌린다.
  - 코드가 컴파일되는지, 동작이 맞는지는 이것만 확실히 판정할 수 있다.
- **추론적 검증**: LLM 코드 리뷰처럼 판단이 필요한 것을 본다.
  - 설계 문제, 규칙 위반, 과설계를 잡는다.
  - 느리고 결과가 매번 조금씩 달라서, 결정적 검증을 대신하지 못한다.
- 완료 판정은 에이전트의 보고가 아니라 실행 결과로 한다. "돌려서 통과했다"는 말은 증거가 아니다.

빌드·테스트 래퍼는 실행(Execution)과 판정(Validation)을 한 번에 한다. 그래서 두 계층에 걸친다.

## 원칙

1. **최소 구성부터 만든다.** 구성요소마다 어떤 실패나 위험을 막는지 설명할 수 있어야 한다. 설명할 수 없으면 넣지 않는다.
2. **강제 장치는 늦게 넣는다.**
   - 처음에는 위험하거나 되돌리기 어려운 행동만 막는다. 시크릿 노출, 파괴적인 git 명령, 자동 생성 파일 편집이 여기에 해당한다.
   - 나머지는 실패가 실제로 관찰된 뒤에 넣는다.
3. **같은 실수는 한 번만 허용한다.** 실패는 [harness-log.md](harness-log.md)에 기록한다. 그리고 아래 기준표에 따라 알맞은 층을 고쳐서 다시 일어나지 않게 한다.
4. **반복되는 실수일수록 결정적인 수단으로 옮긴다.** 아래로 갈수록 강해진다.
   1. 문장 지침
   2. 경로 규칙
   3. 스크립트가 딸린 스킬
   4. 린트·테스트
   5. 훅·권한
5. **항상 읽히는 분량을 작게 유지한다.**
   - 지침은 매 세션 컨텍스트를 차지한다.
   - AGENTS.md는 100줄 이하로 둔다.
   - 특정 상황에만 필요한 내용은 경로 규칙이나 스킬로 옮긴다.
6. **프로젝트마다 다른 사실은 데이터로 둔다.** 스킴, 시뮬레이터, 명령 같은 값은 문장으로 쓰지 않고 프로젝트 설정 파일에 둔다. 스크립트와 지침은 그 파일을 읽는다.
7. **검증 출력은 에이전트가 읽기 좋게 만든다.**
   - 성공하면 한 줄만 출력한다.
   - 실패하면 첫 에러의 파일과 줄 위치부터 보여주고, 원본 로그 위치를 함께 준다.
   - iOS 빌드 로그는 수 MB에 이른다. 그대로 넘기면 컨텍스트를 낭비한다.
8. **에이전트가 앱을 관찰할 수 있게 한다.** 에이전트는 화면을 볼 수 없다. 접근성 식별자, 스크린샷, 로그로 앱 상태를 확인할 수 있어야 동작을 스스로 검증한다.
9. **검증 도구는 에이전트·사람·CI가 같이 쓴다.** 에이전트 전용으로 만들지 않고 프로젝트의 도구로 만든다.
10. **구성요소는 측정하고, 필요 없어지면 뺀다.** 모델이 바뀌면 구성요소를 하나씩 빼보고 결과가 나빠지는지 확인한다.
11. **검사는 작업마다 사람이 고른다.**
    - 문구 한 줄 수정에 E2E까지 돌리면 하네스가 일을 느리게 만든다.
    - 고를 수 있는 검사 목록은 하네스 코드가 아니라 프로젝트 설정에 둔다. 그래야 다른 프로젝트에서도 하네스를 그대로 쓴다.
    - 계획이 필요한 일인지도 사람이 정한다. 작업이 큰지 작은지는 코드를 다 보기 전까지 에이전트도 알기 어렵다.
12. **코드에 남지 않는 결정은 기록하고, 다음 작업 전에 찾아 읽게 한다.**
    - "왜 이렇게 했나"를 모르면 에이전트는 의도된 동작을 버그로 보고 고친다.
    - 기록은 작업을 마무리할 때 남긴다. 무엇을 왜 정했는지 가장 잘 아는 순간이다.

11·12는 여기어때 안드로이드 팀 발표에서 가져왔다 ([ADR 0005](decisions/0005-talk-criteria.md)).

## 실수 → 고칠 층

| 관찰된 실수 | 고칠 곳 | 계층 |
|---|---|---|
| 명령·스킴·경로를 몰라서 헤맨다 | 프로젝트 설정 파일, AGENTS.md 명령 블록 | State, Context |
| 특정 종류의 파일에서 잘못된 패턴을 쓴다 | 경로 규칙 | Context |
| 여러 단계로 된 절차를 틀린다 | 스킬(+스크립트) | Context, Execution |
| 지침이 있는데도 같은 위반을 반복한다 | 린트, 구조 테스트 | Validation (결정적) |
| 결과를 확인할 수단이 없다 | 실행·관찰 도구 | Execution |
| 과설계, 접근성 누락 같은 판단 문제 | 리뷰 서브에이전트 | Validation (추론적) |
| 위험하거나 되돌리기 어려운 행동을 한다 | 권한 deny, 훅 | Enforcement |
| 검증을 건너뛰고 완료를 보고한다 | 검증 강제(관찰될 때만) | Enforcement |

## 상시 로드 예산

항상 컨텍스트에 들어가는 분량의 초기 목표다. 후보 17(평가)에서 측정해 조정한다.

- AGENTS.md는 100줄 이하로 둔다.
- 무조건 로드되는 규칙은 두지 않는다. 모든 규칙에 `paths:`를 달거나 스킬로 만든다.
- 스킬 설명(description)은 스킬당 200자 이하로 쓴다.

## 용어

- **프로젝트 설정 파일**: `.harness/project.json`이다. 프로젝트마다 다른 사실을 모은 JSON 파일이다.
  - 담는 것: 생성기(tuist/xcodeproj/spm), 워크스페이스, 스킴, 시뮬레이터, 명령, 모듈 구조, bundleId
- **경로 규칙**: `.claude/rules/*.md`에 `paths:` 프런트매터를 단 규칙이다. 에이전트가 해당 경로의 파일을 읽을 때만 로드된다.
- **스킬**: 필요할 때만 불러오는 지침 묶음이다. `SKILL.md`에 스크립트나 참고 문서를 곁들인다. 평소에는 이름과 설명만 컨텍스트에 있다.
- **훅**: 에이전트의 특정 행동에 맞춰 자동으로 실행되는 스크립트다. 도구 실행 전후, 세션 시작 같은 시점에 동작한다. 행동을 막거나 피드백을 줄 수 있다.
- **서브에이전트**: 별도 컨텍스트에서 실행되는 에이전트다. 리뷰처럼 독립적인 판단이나 긴 탐색을 맡긴다.
- **플러그인**: 스킬·훅·서브에이전트를 묶어 여러 프로젝트에 배포하는 단위다.
- **jq**: JSON을 읽고 가공하는 명령줄 도구다. macOS에 기본으로 들어 있다. 예: `jq -r '.appScheme' .harness/project.json`
