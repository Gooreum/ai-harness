# 하네스 쉽게 보기

*harness 0.15.0 · 2026-11-10*

AI에게 코드를 맡기면 계획 없이 바로 고치거나, 확인도 안 하고 끝났다고 하거나, 커밋을 빠뜨리곤 합니다. 커밋은 바꾼 내용을 변경 이력에 남기는 일입니다. 하네스는 이런 실수를 줄이는 장치입니다. 이 문서는 하네스가 어떻게 돌아가는지 설명합니다. Claude를 써 본 적 없는 사람도 처음부터 따라 읽을 수 있게, 용어는 처음 나올 때 풀어 씁니다.

두 자료를 기준으로 하네스를 만들었습니다. 첫째는 숙박 앱 여기어때의 안드로이드 팀이 개발자 행사 DroidKnights 2026에서 한 발표 "Workflow AX 적용기"입니다. AX는 AI 전환(AI Transformation)을 줄인 말입니다. 둘째는 발표자 가운데 강래민 님이 만들어 공개한 도구 ai-bouncer입니다. 이 문서에서 "발표"는 첫째 자료를, "발표 팀"은 그 발표를 한 여기어때 안드로이드 팀을 말합니다. 지금 하네스를 깔아 시험하고 있는 앱 세 개(ReadSharp, IntervalTimer, PetCycle)는 "시험장"이라고 부릅니다.

## 1절 · 생각하는 쪽과 실행하는 쪽이 따로 있어요

**Claude**는 Anthropic이 만든 AI입니다. 이런 AI를 LLM(대형 언어 모델)이라고 부릅니다. Claude는 글을 읽고 글을 씁니다. Anthropic의 서버에서 돌아가기 때문에 내 컴퓨터의 파일을 열거나 프로그램을 실행하지 못합니다.

**Claude Code**는 내 컴퓨터에 설치하는 프로그램입니다. 터미널(글자로 명령을 치는 창), 데스크톱 앱, 코드 편집기에서 쓸 수 있습니다. Claude Code는 사람이 친 말을 Claude에게 전합니다. Claude가 파일을 열라고 요청하면 Claude Code가 대신 열고, 그 내용을 Claude에게 돌려줍니다.

Claude Code는 스스로 생각하지 않습니다. 무엇을 할지, 어느 파일을 어떻게 고칠지, 언제 끝낼지는 Claude가 정합니다. Claude Code는 받은 요청을 정해진 방식대로 처리하는 보통 프로그램입니다. 생각하지 않는 프로그램이 Claude의 요청을 어떻게 알아듣는지는 2절에서 설명합니다.

![Claude와 Claude Code, 훅의 관계](images/explained-base.svg)

> Claude는 요청만 하고, 내 컴퓨터에서 파일을 쓰고 명령을 실행하는 쪽은 Claude Code입니다. 그래서 Claude Code 안에 확인 장치를 두면 Claude가 요청한 일은 모두 그 장치를 거칩니다. 확인 장치에는 훅(4절)과 권한(2절 끝)이 있습니다.

먼저 앞으로 자주 나올 용어 네 개를 풀어 둡니다.

- **프롬프트 (prompt)**: AI에게 주는 글을 모두 이렇게 부릅니다. 사람이 친 말뿐 아니라 Claude Code나 하네스가 덧붙이는 글도 들어갑니다. 이 문서에서 "지시"는 하네스가 덧붙이는 글을 말합니다.
- **세션 (session)**: Claude Code를 켜서 나누는 대화 한 묶음입니다. 창을 새로 열면 다른 세션이 되고, 세션마다 고유 번호(세션 ID)가 붙습니다. 한 프로젝트에서 세션 여러 개를 동시에 열 수도 있습니다.
- **턴 · 응답을 마친다 (turn)**: 사람이 한 번 말하면 AI는 메시지를 여러 번 보내며 일합니다. 메시지마다 도구를 요청하거나(도구는 2절), 도구 없이 글만 쓰고 멈춥니다. AI가 무슨 글을 썼든 도구 없이 멈추는 것을 "응답을 마친다"라고 합니다. 응답을 마치면 보통 사람에게 차례가 넘어갑니다. 사람이 말한 때부터 차례가 넘어갈 때까지를 한 턴이라고 합니다. 하네스는 AI가 응답을 마칠 때 일이 정말 됐는지 확인합니다. 덜 됐거나 다음 단계(7절)의 지시가 남았으면 차례를 넘기지 않고 붙잡습니다(4절의 Stop 훅).
- **컨텍스트 (context)**: AI가 한 번에 읽는 글 전체입니다. 담을 수 있는 양에 한도가 있습니다. Claude는 지난 대화를 기억하지 못하기 때문에, Claude Code는 Claude에게 말을 걸 때마다 지금까지의 대화를 모두 다시 보냅니다. AI가 읽은 파일과 명령 출력도 대화에 쌓이므로 긴 로그를 통째로 읽으면 컨텍스트가 금방 찹니다. 대화가 너무 길어지면 Claude Code가 앞부분을 요약해 줄이는데, 요약된 부분은 자세한 내용이 빠집니다.

## 2절 · AI는 도구로만 일해요

Claude Code가 할 수 있는 일을 몇 가지로 정해 둔 것을 **도구**라고 합니다. Claude가 글을 쓰는 것 말고 할 수 있는 일은 도구를 요청하는 것뿐입니다. 파일을 보고, 고치고, 테스트(코드가 맞게 동작하는지 자동으로 확인하는 코드)를 돌리고, 사람에게 질문 창을 띄우는 일은 모두 도구를 요청해서 합니다. Claude가 도구를 요청하면 Claude Code가 실행하고 결과를 돌려줍니다. 그래서 AI를 감독하려면 도구 요청을 보면 됩니다. 이 문서에 Read, Write, Bash 같은 도구 이름이 계속 나오는 것도 이 때문입니다.

### 요청은 정해진 양식으로 씁니다

Claude는 "이 파일 좀 고쳐 줘" 같은 말로 요청하지 않습니다. 메시지 안의 정해진 자리에 아래 같은 양식으로 적습니다. 이런 양식을 **JSON**이라고 합니다. `"이름": 값`처럼 이름과 값을 짝지어 적습니다. 이 문서에서는 이 짝 하나를 칸이라고 부릅니다. 이 문서에 나오는 설정 파일과 진도표도 JSON으로 씁니다. 진도표는 작업이 지금 어느 단계인지 적어 두는 파일로, 7절에서 자세히 봅니다.

```json
{ "name": "Edit",
  "input": { "file_path": "src/login.js", "old_string": "로그인", "new_string": "로그인하기" } }
```

- `name`은 쓸 도구이고, `input`은 도구에 넣을 값입니다. 둘 다 Claude가 정합니다. 이 예는 `src/login.js` 파일에서 "로그인"(`old_string`)을 찾아 "로그인하기"(`new_string`)로 바꾸라는 요청입니다.
- 파일을 열고, 글자를 찾아 바꾸고, 저장하는 코드는 Claude Code 안에 있습니다. Claude는 값만 넘깁니다.
- Bash는 조금 다릅니다. Claude가 넘기는 값이 터미널에 칠 명령 한 줄입니다. `{"name": "Bash", "input": {"command": "npm test"}}`라면 Claude가 쓴 `npm test`(이 프로젝트의 테스트를 돌리는 명령)를 Claude Code가 터미널에 넘겨 그대로 실행합니다. Edit는 정해진 일만 하지만, Bash는 Claude가 쓰는 명령에 따라 무슨 일이든 할 수 있습니다.

Claude Code는 `name`이 Edit면 파일을 고치는 코드를, Bash면 명령을 실행하는 코드를 부릅니다. 스스로 판단하지 않고, 확인은 미리 적어 둔 규칙(이 절 끝의 권한, 4절의 훅)으로 합니다. 예외가 하나 있는데, 위험한 요청인지를 사람 대신 판단하는 AI 판정기를 부르는 경우입니다(이 절 끝).

Claude가 이 양식을 아는 데는 두 가지 이유가 있습니다. 첫째, Claude Code는 말을 걸 때마다 쓸 수 있는 도구 목록을 함께 보냅니다. 목록에는 도구마다 이름, 하는 일, 넣을 값이 적혀 있습니다. 목록에 없는 도구는 요청해도 실행되지 않습니다. 둘째, Claude는 만들어질 때 이 양식으로 요청하도록 훈련받았습니다.

| 도구 | 하는 일 | 예 |
|---|---|---|
| `Read` | 파일을 읽는다 | `login.js` 내용 보기 |
| `Write` | 파일을 새로 쓰거나 통째로 덮어쓴다 | 새 파일 만들기 |
| `Edit` | 파일의 일부만 바꾼다 | 함수 한 줄 고치기 |
| `Bash` | 터미널 명령을 실행한다 | 테스트 명령 `npm test` 실행 |
| `Grep` | 파일 안에서 글자를 찾는다. macOS·Linux용 Claude Code에는 이 도구가 기본으로 없어서, Claude가 Bash로 `grep` 명령을 쓴다 | "login"이 들어간 줄 찾기 |
| `Glob` | 이름으로 파일을 찾는다. macOS·Linux용 Claude Code에는 이 도구가 기본으로 없어서, Claude가 Bash로 `find` 명령을 쓴다 | 이름이 `.js`로 끝나는 파일 찾기 |
| `AskUserQuestion` | 사람에게 선택지가 있는 질문 창을 띄운다 | "큰 일인가요, 작은 일인가요?" 묻기 |
| `Agent` | 다른 AI에게 일을 맡긴다. 이렇게 일을 받는 AI를 서브에이전트라고 한다(6절) | 리뷰 맡기기 |
| `SubagentHandback` | 서브에이전트가 일을 마치고 보고서를 메인 AI(지금 사람과 대화하는 AI)에게 넘긴다. auto 모드(이 절 끝)에서만 주어지고, 없으면 서브에이전트의 마지막 답이 보고서가 된다 | 리뷰 결과 넘기기 |

### 일 하나를 하는 동안 아래 과정이 여러 번 되풀이됩니다

1. Claude Code가 지금까지의 대화와 도구 목록을 Claude에게 보냅니다.
2. Claude가 메시지를 보냅니다. 글과 함께 도구를 요청하거나, 도구 없이 글만 씁니다.
3. 도구 요청이 있으면 Claude Code가 실행합니다. 그 결과(파일 내용, 명령 출력, 에러)를 대화에 붙이고 1로 돌아갑니다.
4. 도구 없이 글만 왔으면 응답을 마친 것입니다. Stop 훅(4절)이 붙잡지 않으면 턴이 끝납니다.

예를 들어 "화면 코드를 역할별로 나눠 정리해 줘"라고 시켰다고 해 봅시다. 여러 파일을 고치는 큰 작업입니다. 일은 이렇게 흘러갑니다.

1. Claude가 구조를 보려고 Bash로 파일 목록을, Read로 주요 파일 내용을 요청합니다. Claude Code가 목록과 내용을 돌려줍니다.
2. Claude가 읽은 내용을 보고 무엇을 어떻게 나눌지 정합니다. 다음 도구 요청을 보내기 전에 Claude 안에서 하는 일이라, 따로 메시지가 오가지 않습니다.
3. Claude가 새 파일은 Write로 만들어 달라고, 기존 파일은 Edit로 고쳐 달라고 하나씩 요청합니다. Claude Code가 요청대로 처리합니다.
4. Claude가 Bash로 빌드(코드를 묶어 실행할 수 있는 앱으로 만드는 일)와 테스트를 요청하면, Claude Code가 실행하고 출력을 돌려줍니다.
5. 에러가 있으면 Claude가 출력을 읽고 3(파일 고치기)으로 돌아갑니다. 에러가 없다고 판단하면 글로 보고하고 응답을 마칩니다.

언제 끝낼지도 Claude가 정하므로, 4(빌드와 테스트)를 건너뛰고 끝낼 수도 있습니다. 이런 일을 막으려고 하네스를 둡니다(3절).

### 도구가 필요한 이유

- **파일을 열어 보지 않고 한 답은 추측입니다.** 함수 이름이나 설정 값을 그럴듯하게 지어내도, 실제 파일과 다르면 틀린 답입니다.
- **파일을 바꾸려면 도구를 써야 합니다.** AI가 대화창에 코드를 적어 줘도 파일은 그대로입니다. Edit나 Write, Bash 같은 도구를 써야 바뀝니다.
- **확인도 도구로 합니다.** 테스트를 통과하는지는 Bash로 돌려 봐야 압니다.

도구는 Claude Code가 실행합니다. 그래서 Claude Code는 도구를 실행하기 직전과 직후에 다른 프로그램을 끼워 넣어 돌릴 수 있습니다. 이 프로그램이 4절에서 자세히 볼 훅입니다. 직전에 도는 훅은 실행을 막을 수 있고, 직후에 도는 훅은 도구 결과에 메모를 붙여 AI에게 전할 수 있습니다. 훅은 도구 이름과 넣은 값을 보고 판단합니다. 뒤에서도 "Write로 진도표(7절)의 단계를 바꾸면 막는다", "Bash로 진도표를 지우려 해도 막는다"처럼 도구 이름을 들어 설명합니다.

**권한 (permission)**: Claude Code가 도구를 실행하기 전에 해도 되는지 판단할 때 따르는 규칙입니다. 허용(`allow`), 매번 사람에게 묻기(`ask`), 항상 거부(`deny`) 세 가지가 있습니다. 규칙은 프로젝트 폴더 안 `.claude` 폴더의 `settings.json` 파일에 적습니다. 경로로 쓰면 `.claude/settings.json`입니다. 하네스는 비밀 파일(`.env`, `credentials.json`, 안드로이드 서명 키 `.jks`·`.keystore` 등)을 `deny` 목록에 넣어, AI가 Read 도구나 `cat` 같은 명령으로 읽지 못하게 합니다. 이 목록에 없는 키 파일은 막지 않습니다.

사람에게 묻는 일을 줄여 주는 auto 모드를 켜면, Claude Code는 사람 대신 AI 판정기에게 위험한 요청인지 묻기도 합니다. 이 판정기는 Claude Code가 부르는 것이고, 일을 하는 Claude와는 따로 돌아갑니다.

<a id="s3"></a>
## 3절 · 지침에 적어 둬도 지키지 않을 때가 있어요

AI에게 코드를 맡기면 아래 같은 일이 되풀이됩니다. 항목 아래에는 하네스가 그 일을 어떻게 다루는지 설명한 절을 적었습니다.

- 계획을 세우지 않고 바로 코드를 고칩니다.
  - 다루는 곳: 7절 작업 흐름의 계획 단계.
- 테스트를 돌리지 않고 "다 했어요"라고 보고합니다.
  - 다루는 곳: 9절 검사.
- 테스트를 통과하려고 테스트 조건을 느슨하게 바꿉니다.
  - 다루는 곳: 10절 리뷰. 사람이 작업을 시작할 때(7절) 고르는 검사 목록에 리뷰를 넣으면, 다른 AI(리뷰어)가 바뀐 테스트도 읽습니다. 다만 리뷰도 AI의 판단이라 이 일을 완전히 막지는 못합니다.
- 프로그램이 자동으로 만드는 파일(자동 생성 파일)을 AI가 고칩니다. 그 파일을 다시 만들면 고친 내용이 사라집니다.
  - 다루는 곳: 13절.
- 지침 파일(아래)에 "끝나면 커밋해"라고 써 둬도 잊습니다.
  - 다루는 곳: 12절.
- 팀이 일부러 그렇게 만든 코드를 버그로 알고 고쳐 버립니다. 왜 그렇게 만들었는지가 코드에 적혀 있지 않아서입니다.
  - 다루는 곳: 11절 위키.

가장 쉬운 대책은 지침을 적어 두는 것입니다. Claude Code는 세션을 열 때마다 프로젝트 폴더의 **지침 파일** `CLAUDE.md`를 읽어 AI에게 줍니다. Codex 같은 다른 AI 코딩 도구는 `AGENTS.md` 파일을 읽습니다. 하네스는 이런 도구도 같은 지침을 읽게 하려고 지침을 `AGENTS.md`에 씁니다. Claude Code는 `CLAUDE.md`가 없을 때만 `AGENTS.md`를 읽습니다. 그런데 `CLAUDE.md`는 프로젝트에 이미 있는 경우가 많고, Claude Code에만 줄 지침을 적는 자리로도 씁니다. 그래서 하네스는 `CLAUDE.md`에 `AGENTS.md`도 읽으라는 한 줄(`@AGENTS.md`)을 넣습니다. 특정 파일을 열 때만 함께 읽히는 지침도 있습니다. `.claude/rules/`에 두는 **경로 규칙**입니다. 예를 들어 위키(11절) 파일을 열면 위키 쓰는 법이 함께 읽힙니다.

다만 지침은 부탁이라 지키게 할 힘이 없고, 길어지면 AI가 놓치기도 합니다. 발표 팀도 같은 문제를 겪었습니다. 그래서 하네스는 중요한 일을 지침에만 맡기지 않고, 훅(4절)이 확인하게 합니다.

<a id="s4"></a>
## 4절 · 훅은 정해진 순간에 저절로 돌아요

**훅**(hook)은 Claude Code가 정해진 순간에 자동으로 실행하는 작은 프로그램(스크립트)입니다. AI가 부르지 않아도 Claude Code가 부릅니다. 어느 순간에 어떤 스크립트를 실행할지는 설정 파일에 적어 둡니다. 하네스는 이 설정을 플러그인(6절) 안에 넣어 두었습니다.

도구 실행 전 훅이 안 된다고 답하면 Claude Code는 그 도구를 실행하지 않습니다. 1절에서 본 대로 AI의 도구 요청은 빠짐없이 Claude Code를 거치고, 그때 훅도 거칩니다. 다만 훅은 도구 이름과 넣은 값만 보므로, 명령이 실제로 무슨 일을 하는지까지 다 알지는 못합니다. 이런 빈틈은 13절에 모아 두었습니다.

요청과 실행이 되풀이되다가 Claude가 응답을 마칩니다. 이 과정에서 훅이 끼어드는 자리는 여럿인데, 하네스가 주로 쓰는 자리는 세 곳입니다.

![훅 세 자리](images/explained-hooks.svg)

> 빨강은 도구가 실행되기 전에 막는 자리입니다. 주황은 실행 뒤에 메모를 붙이는 자리와, 응답 끝에 턴을 붙잡는 자리입니다.

### 도구 실행 전 · PreToolUse

아직 실행 전이라, 훅이 막으면 아무 일도 일어나지 않습니다.

하네스에서 AI가 진도표(7절)를 쓸 수 있는 것은 작업을 시작하거나 이어서 하거나 취소할 때뿐입니다. 그 밖의 경우에 진도표를 쓰거나 지우려 하면 훅이 막습니다. 그래서 AI가 단계를 다음 단계로 바꿔 저장하려 해도 막힙니다. 단계를 넘기는 일은 Stop 훅이 합니다(아래). 자동 생성 파일을 Edit나 Write로 고치려 할 때도 이 자리의 훅이 막습니다.

### 도구 실행 후 · PostToolUse

이미 실행했으니 되돌리지 못합니다. 대신 AI에게 메모를 남길 수 있습니다. Claude Code가 도구 결과를 Claude에게 보낼 때 그 메모를 함께 넣습니다.

하네스에서는 AI가 작업을 시작하거나 이어서 하려고 진도표를 저장하면, 훅이 이번 단계에서 할 일을 메모로 붙입니다. 또 리뷰어(10절)가 파일을 열면 훅이 그 파일 이름을 적어 둡니다. 이것은 AI에게 남기는 메모가 아니라 훅이 따로 남기는 기록입니다. 리뷰어가 바뀐 파일을 정말 다 열어 봤는지는, 리뷰어가 일을 끝낼 때 도는 훅(아래 `SubagentStop` 자리, 10절)이 이 기록을 보고 확인합니다.

### 응답이 끝날 때 · Stop

AI가 도구 없이 멈추면 Claude Code가 Stop 훅을 부릅니다. 훅이 붙잡으면 Claude Code는 턴을 끝내지 않습니다. 훅이 쓴 이유를 대화에 붙여 Claude에게 다시 보내고, 2절의 과정이 한 번 더 되풀이됩니다. AI는 그 이유를 읽고 일을 이어 갑니다.

하네스의 Stop 훅은 AI가 쓴 글을 읽지 않습니다. AI가 "다 했어요"라고 쓰든 질문을 쓰든, 훅에게는 똑같이 응답이 끝난 것입니다. Claude Code가 넘겨준 정보에서는 세션 ID, 프로젝트 폴더, 돌고 있는 서브에이전트 목록 같은 값만 읽습니다. 그리고 그 폴더에서 진도표, 검사 결과, git 상태(커밋하지 않은 변경이 있는지 등)를 찾아봅니다. git은 변경 이력을 기록하는 프로그램입니다(6절).

이 훅은 검증 단계(7절)에서 검사가 실패했거나, 마무리 단계에서 커밋과 push(원격 서버에 올리기, 12절)를 안 했으면 붙잡습니다. 확인을 통과하면 훅이 진도표를 다음 단계로 넘깁니다. 이때도 바로 놓아주지 않고, 다음 지시를 주려고 붙잡습니다. 작업은 마무리 단계까지 통과해야 끝납니다. 그 전에 놓아주는 경우는 13절에 있습니다.

하네스가 쓰는 자리는 두 곳이 더 있습니다. 세션을 열 때(`SessionStart`)와 서브에이전트가 일을 끝낼 때(`SubagentStop`)입니다. 각각 8절과 10절에 나옵니다.

### 훅이 막는 방법

- 프로그램은 입력(stdin)으로 글을 받습니다. 글을 내보내는 곳은 출력(stdout)과 오류 출력(stderr) 두 가지입니다. 훅은 Claude Code가 넘겨준 상황 설명을 입력으로 받습니다. 도구 실행 전후에 도는 훅은 2절에서 본 `name`과 `input`을 `tool_name`, `tool_input`이라는 이름으로 받습니다. 값은 AI가 쓴 그대로입니다. 그래서 훅은 Write라면 `file_path`가 진도표인지 보고, Bash라면 `command`에 진도표를 쓰거나 지우는 명령이 들어 있는지 봅니다.
- 프로그램은 끝날 때 숫자 하나를 남깁니다. 이 숫자를 **종료 코드**(exit code)라고 합니다. 0이면 성공이고, 다른 숫자면 실패입니다.
- 훅이 종료 코드 2로 끝나면 Claude Code는 막으라는 뜻으로 받아들입니다. 도구 실행 전 자리라면 도구를 실행하지 않고, Stop 자리라면 턴을 끝내지 않습니다(Stop 자리의 드문 예외는 13절). 이때 훅이 오류 출력에 쓴 이유가 AI에게 전해집니다. 1 같은 다른 실패 코드로 끝나면 막지 않습니다. 도구 실행 전 자리라면 도구가 실행되고, Stop 자리라면 턴이 끝납니다.
- 종료 코드 0으로 끝나면서 출력에 JSON을 쓰는 방법도 있습니다. 거부한다는 결정을 적으면 막고, 메모를 적으면 그 메모가 AI에게 전해집니다. Stop 자리에서 메모를 내보내면 턴이 끝나지 않고, AI는 그 메모를 받아 한 번 더 응답합니다. 종료 코드 2로 막을 때와 다른 점은 Claude Code가 이것을 훅 오류로 보지 않고 훅이 남긴 안내로 보여 준다는 것입니다. 하네스는 같은 단계에서 10번 연속 붙잡은 뒤에 이 방법을 씁니다. 메모를 보내 AI가 사람에게 어떻게 할지 묻게 합니다(13절).

<a id="s5"></a>
## 5절 · 하네스는 여러 장치를 한데 묶은 것이에요

**하네스**(harness)는 원래 말에 채우는 마구를 뜻하는 영어 단어입니다. 미리 정해 둔 방식대로 AI가 일하게 묶어 두는 장치를 이렇게 부릅니다. 이 문서가 설명하는 하네스는 GitHub의 Gooreum 계정에 있는 저장소 ai-harness에 들어 있습니다. 여러 프로젝트에 이 하네스를 똑같이 깔아 씁니다. 저장소가 무엇인지는 6절에서 설명합니다.

이 문서에 계속 나오는 것을 아래 표에 모았습니다. 표의 첫 세 줄은 하네스와 함께 일하는 쪽이고, 나머지는 하네스를 이루는 부품과 파일입니다.

| 이름 | 가리키는 것 | 하는 일 |
|---|---|---|
| 사람 | 개발자 | 요청하고, 모드와 검사를 고르고(7절), 계획을 승인합니다. PR(내 작업을 기본 코드에 합쳐 달라는 요청)을 올릴지, 머지(합치기)할지도 정합니다(12절) |
| AI | Claude | 코드를 읽고 고치고, 검사를 돌리고, 보고합니다 |
| Claude Code | 내 컴퓨터에서 돌아가는 프로그램 | AI의 도구 요청을 실행하고, 정해진 순간에 훅을 부릅니다 |
| 지침 | `AGENTS.md`, 경로 규칙 | AI가 지킬 일이 적혀 있습니다(3절) |
| 훅 | `plugin/hooks/`의 스크립트 7개 | 정해진 순간(4절)에 허용되지 않은 도구 실행을 막고, 검사 결과와 커밋 여부를 확인해 진도표의 단계를 넘깁니다 |
| task 스킬 | 작업을 시작하는 절차서(스킬은 6절) | AI가 이 절차대로 모드와 검사를 묻고 진도표를 만듭니다(7절) |
| 진도표 | `.harness/state/task.json` | 지금 하는 작업과 그 작업의 단계를 담습니다(7절) |
| 검사 스크립트 | `record`, `passed` | `record`는 검사를 돌려 결과를 남기고, `passed`는 그 결과가 통과였는지, 최신인지 판정합니다(9절) |
| 리뷰어 | `harness:reviewer` 서브에이전트 | 바뀐 코드를 읽고 문제를 찾습니다(10절) |
| 위키 | `docs/wiki/` | 팀이 정한 규칙과 그 이유, 확인한 기술 사실을 모아 둔 곳입니다(11절) |

<a id="s6"></a>
## 6절 · 파일은 세 곳에 나뉘어 있어요

먼저 용어 몇 개를 짚고 갑니다. **저장소**(repository)는 프로젝트 파일 전체와 그 변경 이력을 담은 폴더입니다. 변경 이력은 앞에서 본 **git**으로 기록하고, 이력에 지금 상태를 한 번 저장하는 것이 **커밋**입니다. git에 기록하지 않을 파일은 `.gitignore`라는 목록에 적습니다. 이름이 점(`.`)으로 시작하는 폴더(`.harness`, `.claude`)는 평소에 숨겨져 있습니다. 프로젝트의 맨 위 폴더는 **루트**라고 부릅니다.

Claude Code에 기능을 더하는 부품은 훅(4절) 말고도 세 가지가 있습니다.

- **스킬 (skill)**: 특정한 일을 할 때 AI가 불러와 읽는 절차서입니다. 평소에는 이름과 한 줄 설명만 AI에게 보이고, 필요할 때 AI가 본문을 엽니다.
- **서브에이전트 (subagent)**: 메인 AI가 일을 맡기려고 따로 띄우는 AI입니다. 메인 AI는 지금 사람과 대화하고 있는 Claude를 말합니다. 서브에이전트는 대화를 새로 시작하므로 메인 AI의 대화 내용을 모릅니다. 서브에이전트가 읽은 파일도 메인 AI의 컨텍스트에 쌓이지 않습니다. 띄울 때 쓸 수 있는 도구를 정해 둘 수도 있습니다.
- **MCP**: AI에게 새 도구를 붙이는 표준 방식입니다. 따로 돌아가는 프로그램(MCP 서버)이 Claude Code에 자기 도구 목록을 알리면, AI가 그 도구를 쓸 수 있습니다. 하네스에는 앱 시험에 쓰는 `harness-network`라는 MCP 서버가 있습니다. 앱은 보통 인터넷의 진짜 서버에서 데이터를 받아 옵니다. 시험할 때는 개발자가 앱 코드에서 요청 주소를 `harness-network` 쪽으로 바꿔 둡니다. 그러면 이 서버가 진짜 서버 대신 가짜 응답을 돌려줍니다. AI는 이 서버가 알려 준 도구로 어떤 요청에 어떤 응답(서버 오류, 느린 응답, 빈 응답)을 돌려줄지 정하고, 앱이 그 상황에서 어떻게 동작하는지 시험합니다.

훅과 이 부품들을 한 묶음으로 만든 것이 **플러그인**(plugin)입니다. 하네스의 플러그인 이름은 `harness`이고, 그 안의 부품은 `harness:reviewer`처럼 "플러그인 이름:부품 이름"으로 부릅니다.

하네스의 파일은 세 곳에 있습니다. 하네스 저장소, 하네스를 깐 프로젝트 저장소, 그리고 Claude Code에 설치된 플러그인입니다. 그림은 세 곳에 무엇이 있는지 보여 줍니다.

![파일이 놓이는 세 곳](images/explained-files.svg)

> 하네스 저장소의 `template` 폴더에는 프로젝트에 깔 파일의 원본이 있습니다. 설치 명령 `init`(14절)이 이 파일들을 프로젝트에 복사합니다. 복사한 파일은 사람이 프로젝트의 git에 커밋합니다. `plugin` 폴더는 Claude Code에 설치됩니다. 프로젝트의 `.claude/settings.json`에는 이 플러그인을 켜는 설정과, 비밀 파일을 읽지 못하게 하는 권한 규칙(2절)이 들어갑니다. 작업하는 동안에만 쓰는 파일은 `.gitignore`에 적어 커밋하지 않습니다. 그림의 `task.owner` 같은 작은 파일은 8절 흐름의 5번에서 하나씩 설명합니다.

파일이 놓이는 곳과 별개로, 하네스가 동작하려면 아래 세 조건을 채워야 합니다.

- 프로젝트의 `.claude/settings.json`에서 플러그인을 켜 두어야 합니다. 그래야 그 프로젝트의 세션에서 훅이 돌고 스킬을 쓸 수 있습니다.
- 그 프로젝트에서 일하는 사람마다 컴퓨터에 플러그인 파일이 있어야 합니다. 프로젝트를 처음 열 때 "이 폴더를 믿을지" 묻는 창에서 허용하면, Claude Code가 설정에 적힌 곳에서 플러그인을 받아 와 켭니다. 그래도 플러그인이 보이지 않으면 직접 설치합니다(14절).
- 프로젝트에 설정 파일 `.harness/project.json`이 있어야 합니다. 플러그인이 켜져 있어도 이 파일이 없으면 훅은 아무것도 막거나 확인하지 않습니다. Bash로 진도표를 쓰는 명령을 막는 것만 예외입니다. 이 파일에는 자동 생성 파일 목록(`generated`) 같은 설정이 들어갑니다. `harness-network`가 동작하려면 이 파일에 포트 번호(`e2e.network.port`)까지 적어야 합니다. 포트 번호는 서버가 요청을 받는 창구 번호입니다.

<a id="s7"></a>
## 7절 · 일은 단계를 밟고, 단계는 Stop 훅이 넘겨요

작업을 시작하면 AI는 Write로 프로젝트 안에 진도표 `.harness/state/task.json`을 만듭니다. 예를 들면 이렇습니다.

```json
{ "title": "로그인 버그 수정", "mode": "plan", "stage": "plan", "checks": ["unit-test", "review"] }
```

- `mode`(모드)는 일을 진행하는 방식입니다. `plan`은 계획부터 세우는 방식이고 큰 일에 씁니다. `simple`은 바로 고치는 방식이고 작은 일에 씁니다. 이 예에서는 로그인 버그가 여러 화면에 걸쳐 있다고 보고 사람이 plan을 골랐습니다.
- `stage`(단계)에는 지금 어느 단계에 있는지 적습니다.
- `checks`(검사)에는 이번에 돌릴 검사의 이름을 적습니다. 검사는 테스트나 리뷰처럼 일이 제대로 됐는지 보는 항목입니다(9절).

모드마다 밟는 단계는 이렇습니다.

- **plan 모드**: 계획(plan) → 구현(implement) → 검증(verify) → 마무리(finish) → 끝(done)
- **simple 모드**: 구현(implement) → 검증(verify) → 마무리(finish) → 끝(done)

AI는 지금 단계의 일을 하고 응답을 마칩니다. 그러면 Stop 훅이 그 단계의 조건을 확인합니다. 검증 단계의 조건은 검사 통과이고, 마무리 단계의 조건은 커밋과 push(12절)입니다. 조건을 채우지 못했으면 Stop 훅은 단계를 그대로 두고 이유를 주며 붙잡습니다. 조건을 채웠으면 진도표의 `stage`를 다음 단계로 바꾸고, 다음 지시를 주며 붙잡습니다. 마무리 단계를 통과하면 `stage`를 done으로 바꾸고 턴을 끝내게 둡니다. 계획 단계와 구현 단계에서는 따로 볼 조건이 없어서, AI가 응답을 마치면 바로 다음 단계로 넘어갑니다.

### 모드와 검사는 사람이 골라요

진도표를 만들기 전에 AI는 플러그인의 `task` 스킬을 불러옵니다. 그리고 그 절차대로 질문 창(`AskUserQuestion`)을 띄워 plan과 simple 가운데 무엇으로 할지, 어떤 검사를 돌릴지 묻습니다. 검사 선택지는 프로젝트의 `.harness/checks.json`에 적힌 목록입니다. 질문 하나에 넣을 수 있는 선택지는 네 개까지인데, 검사 질문에는 늘 "고르지 않음"을 하나 넣습니다. 그래서 검사는 질문 하나에 세 개씩 나눠 묻습니다. 사람이 요청하면서 모드와 검사를 이미 말했다면 묻지 않습니다.

발표 팀이 재 보니 모드에 따라 결함 비율이 크게 달랐습니다. 여러 화면을 건드리는 큰 작업을 simple로 했더니 9번 가운데 7번(78%)에서 결함이 나왔고, plan으로 했을 때는 4번 가운데 1번(25%)이었습니다. 그런데 AI는 코드를 다 보기 전에는 작업이 큰지 작은지 잘 알지 못했습니다. 요청한 사람은 일의 범위를 알고 있으므로, 발표 팀은 모드를 사람이 고르기로 했습니다. 하네스도 그렇게 합니다.

### AI가 진도표를 쓸 수 있는 경우

AI는 아래 세 경우에만 Write나 Edit로 진도표를 쓸 수 있습니다.

- **시작**: 진도표가 없거나 지난 작업이 done이면, `stage`에 그 모드의 첫 단계를 적어 새 작업을 엽니다. 첫 단계는 plan 모드면 `plan`, simple 모드면 `implement`입니다.
- **이어서 하기**: 진행 중인 작업을 같은 모드, 같은 단계로 다시 저장합니다. 세션을 새로 열었을 때 이렇게 하면 지금 단계의 지시를 다시 받습니다. 사람이 "리뷰도 하자"라고 하면 이때 검사를 더할 수 있습니다. 검사를 빼고 저장하면 훅이 막습니다.
- **취소**: 사람이 "그만하자"라고 하면 `stage`를 `"done"`으로 하고 `cancelled: true`를 더해 저장합니다.

그 밖의 쓰기는 PreToolUse 훅 `guard-state.sh`가 막습니다. `stage`를 다음 단계로 바꿔 저장하는 것이 그 예입니다. Bash로 진도표를 쓰거나 지우는 흔한 명령은 이 세 경우에도 막습니다.

발표 팀의 방식에서는 AI가 진도표의 단계를 고쳐 적었습니다. 하네스도 처음엔 그렇게 했습니다. 당시 훅은 AI가 Write나 Edit로 단계를 바꿔 저장할 때만 검사를 통과했는지 확인했습니다. 그런데 시험장 세 곳 가운데 IntervalTimer(운동 타이머 앱)와 ReadSharp(영어 공부 앱) 두 곳에서 AI가 작업을 시작하며 Bash로 진도표를 만든 일이 있었습니다. AI가 쓴 명령은 `cat > task.json`처럼 파일에 글을 써넣는 명령이었고, 진도표를 확인하는 훅은 돌지 않았습니다. 두 번 모두 AI가 곧 Write로 다시 저장해서 문제없이 지나갔습니다. 하지만 같은 방법으로 단계를 넘겼다면 훅은 검사를 건너뛴 것을 잡지 못했을 것입니다.

단계를 누가 넘길지는 발표 대신 ai-bouncer를 따랐습니다. ai-bouncer에서는 `bouncer start` 명령이 진도표를 만들고, 단계는 Stop 훅만 넘깁니다. 하네스도 단계를 넘기는 일을 Stop 훅에 맡겼습니다. 이렇게 하면 정상적인 작업에서 AI가 단계를 바꿀 일이 없습니다. 그래서 앞에서 본 것처럼, 단계를 넘기려는 저장은 검사를 통과했든 안 했든 훅이 막습니다. 훅이 아직 알아보지 못하는 명령은 13절에 있습니다. 이 결정은 설계 결정 기록(16절)에 남겼습니다.

AI가 사람에게 물을 것이 있으면 질문 창으로 묻습니다. 질문 창도 도구라서, AI가 질문 창을 띄우면 Claude Code는 사람이 답할 때까지 기다렸다가, 그 답을 도구 결과로 AI에게 돌려줍니다. 이때 AI는 응답을 마친 것이 아닙니다. AI가 글로만 묻고 응답을 마치면 Stop 훅은 질문인 줄 모르고 평소처럼 확인합니다. 계획 단계였다면 사람이 답하기 전에 구현 단계로 넘어갑니다.

Claude Code에는 Plan 모드라는 기능이 따로 있습니다. 이 모드에서 AI는 코드를 고치지 않고 계획만 세운 뒤, 계획 창을 띄워 사람의 승인을 받습니다. 하네스의 plan 모드와는 다른 기능이지만, 하네스는 계획 단계에서 이 창을 빌려 씁니다. 이 창으로 승인을 받으라고 지시만 하고, 승인을 받았는지는 확인하지 않습니다.

## 8절 · "로그인 버그 고쳐 줘" 하나가 끝날 때까지

아래 그림은 plan 모드를 고르고, 검사로 unit-test(단위 테스트, 함수 하나하나를 확인하는 테스트)와 review(코드 리뷰)를 골랐을 때 일이 흘러가는 순서를 보여 줍니다. 사람, AI, 훅, 파일을 세로 줄 네 개로 나눴고, 시간은 위에서 아래로 흐릅니다.

![로그인 버그 수정 작업의 전체 흐름](images/explained-flow.svg)

> 빨강 상자는 도구 실행 전 훅(막을 수 있음), 주황 상자는 도구 실행 후 훅과 Stop 훅, 초록 상자는 통과입니다. 주황 화살표는 훅이 AI에게 주는 지시입니다. 진도표의 단계를 바꾸는 상자는 모두 훅 줄에 있습니다.

### 번호별 설명

1. **세션 열림**: `SessionStart` 훅 `session-start.sh`는 세션을 새로 열 때와 지난 세션을 다시 열 때 실행됩니다. `/clear` 명령으로 대화를 비운 뒤나 긴 대화를 요약해 줄인 뒤에도 실행됩니다. 진행 중인 작업이 없으면 "코드 작업은 task 스킬로 시작하라"라고 알려 줍니다. 있으면 "지금 ○○ 단계다. 이어서 하려면 진도표를 같은 내용으로 다시 저장해 지시를 받으라"라고 알려 줍니다.
2. **요청**: 사람이 "로그인 버그 고쳐 줘"라고 시킵니다.
3. **모드·검사 고르기**: AI가 `task` 스킬을 불러와 질문 창으로 묻습니다. 모드는 plan(계획부터)과 simple(바로 구현) 가운데 하나입니다. 검사 선택지는 `checks.json`에 적힌 목록입니다. 사람이 plan을 고르고, 검사는 unit-test와 review를 고릅니다.
4. **진도표 만들기**: AI가 Write로 `.harness/state/task.json`을 만듭니다. 내용은 `{title, mode: "plan", stage: "plan", checks: ["unit-test", "review"]}`입니다. Write 직전에 PreToolUse 훅 세 개가 실행되는데, 그 가운데 `guard-state.sh`가 새 작업을 그 모드의 첫 단계로 여는지 봅니다. 다른 단계로 열려 하면 막습니다. 이 훅은 Bash로 진도표를 쓰거나 지우는 명령도 막습니다. 다만 자주 쓰는 명령 형태만 알아보므로 놓치는 명령이 있습니다(13절).
5. **시작 기록과 첫 지시**: Write가 끝나면 PostToolUse 훅 `stage-context.sh`가 작은 파일 여섯 개를 만듭니다.
   - `task.owner`: 이 세션이 작업 주인이라는 표시
   - `task.started`: 시작 시각
   - `task.base`: 작업을 시작할 때 있던 마지막 커밋. 나중에 무엇이 바뀌었는지 볼 때 비교 기준
   - `task.wip`: 시작할 때 이미 바뀌어 있던 파일 목록
   - `task.history`: 일지. 첫 줄은 작업 시작 기록
   - `task.seen`: 훅이 마지막으로 본 단계. 새 작업인지 가리는 기준

   이어서 도구 결과에 메모를 붙입니다. 메모에는 지시가 두 가지 들어 있습니다. 하나는 "계획만 세운다"는 하네스의 지시입니다. 다른 하나는 프로젝트가 `checks.json`의 계획 단계 칸에 적어 둔 "위키부터 찾아라"입니다.
6. **위키 찾기**: AI가 `scripts/harness/wiki search 로그인`을 실행합니다. 이 스크립트는 `docs/wiki/`에서 검색어가 모두 들어간 기록을 찾아 보여 주고, 검색어를 `wiki-search.log`에 적어 둡니다. 요청이 기록과 어긋나면 AI는 바로 고치지 않고 사람에게 묻습니다.
7. **계획과 승인**: AI가 계획을 쓰고 Claude Code의 계획 창으로 승인을 받습니다. 물을 게 있으면 질문 창으로 묻습니다. 승인을 받으라는 말은 지시에만 있고, 훅은 승인을 받았는지 확인하지 않습니다.
8. **구현 단계로 넘김**: AI가 응답을 마치면 Stop 훅 `stop-gate.sh`가 실행됩니다. 이 세션이 작업 주인인지, 작업이 done이 아닌지, 서브에이전트를 기다리는 중이 아닌지 봅니다. 계획 단계는 따로 볼 조건이 없으므로, Stop 훅은 `stage`를 plan에서 implement로 바꾸고 일지에 단계를 넘겼다는 뜻으로 advance라고 적습니다. 그런 다음 구현 지시를 주며 종료 코드 2로 붙잡습니다. AI는 턴을 끝내지 못하고 구현을 시작합니다.
9. **코드 고치기**: AI가 Edit로 `src/login.js`를 고칩니다. Edit 직전에 PreToolUse 훅 세 개가 실행됩니다.
   - `tool-count.sh`: 도구를 쓴 횟수를 셉니다. Stop 훅은 이 숫자로 AI가 도구를 썼는지 봅니다(13절 "같은 이유로 되풀이되면 놓아주기").
   - `protect-generated.sh`: 고치려는 파일이 `project.json`의 `generated`에 적힌 자동 생성 파일이면 막습니다.
   - `guard-state.sh`: 고치려는 파일이 진도표가 아니니 막지 않습니다.

   Edit가 끝난 뒤 `stage-context.sh`도 실행되지만, 진도표를 쓴 게 아니라서 아무것도 하지 않습니다.
10. **검증 단계로 넘김**: AI가 다시 응답을 마치면 Stop 훅이 `stage`를 implement에서 verify로 바꾸고 일지에 적습니다. 이번에 주는 지시에는 하네스의 검증 지시가 먼저 들어갑니다. 요청과 대조해 빠진 일이 없는지 확인하고, 검사를 하나씩 실행해 출력을 보라는 내용입니다. 그 뒤로는 사람이 고른 검사마다 프로젝트가 prompt 칸(9절)에 적어 둔 지시가 `checks.json` 순서대로 붙습니다.
11. **테스트**: AI가 `scripts/harness/record unit-test npm test`를 실행합니다. 결과는 `.harness/out/unit-test.json`과 `.harness/out/unit-test.log`에 남습니다(9절).
12. **리뷰 맡기기**: AI가 리뷰어 `harness:reviewer`에게 리뷰를 맡깁니다. 리뷰어는 바뀐 파일과, 그 코드를 불러 쓰는 다른 파일을 Read로 엽니다. 리뷰어가 Read로 파일을 열 때마다 PostToolUse 훅 `review-record.sh`가 그 파일 이름을 적어 둡니다. 리뷰어를 메인 AI와 따로(백그라운드로) 돌렸다면, 리뷰어가 끝날 때까지 Stop 훅은 붙잡지도 않고 단계를 넘기지도 않습니다(13절).
13. **리뷰 판정**: 리뷰어가 일을 끝내면 `SubagentStop` 자리에서 같은 스크립트가 판정합니다. 조건은 둘입니다.
    - 바뀐 파일을 모두 열었어야 합니다. Read로 열지 않고 검색으로 내용을 훑기만 한 파일은 연 것으로 치지 않습니다. 열지 않아도 되는 파일은 이렇습니다.
      - 이미지나 글꼴처럼 글자로 된 내용이 없는 파일
      - 라이브러리 버전을 고정해 두는 lock 파일
      - 자동 생성 파일과 지운 파일
      - 아직 커밋하지 않은 새 파일 가운데 작업 전부터 있었고 그 뒤로 고치지 않은 것. git에는 새 파일로 잡히지만 이번 작업이 만든 파일이 아닙니다
    - 보고서에 "`요약 · 차단 0`"이라는 줄과 "`발견 없음`"으로 시작하는 줄 가운데 하나가 있어야 합니다. 차단은 꼭 고쳐야 할 문제를 말합니다.

    둘 다 맞으면 `.harness/out/review.json`에 통과로 쓰고, 아니면 실패와 그 이유를 씁니다.
14. **검사 확인**: AI가 응답을 마치면 Stop 훅이 검사 결과를 확인합니다. 사람이 고른 검사마다 run 칸(9절)의 명령을 프로젝트 루트에서 차례로 실행하는 방식입니다. 여기서는 `passed unit-test`와 `passed review`입니다. Stop 훅이 run 명령을 기다리는 시간은 모두 합쳐 1700초까지이고, 넘기면 검사가 실패한 것으로 칩니다. 하네스는 Stop 훅 자체의 제한 시간을 ai-bouncer와 같은 1800초로 두었습니다. 훅이 이 시간을 넘기면 Claude Code가 중단시키기 때문에 검사 시간은 그보다 짧게 잡았습니다. `passed`가 무엇을 보는지는 9절에 있습니다.
15. **실패 처리**: 검사가 하나라도 실패하면 Stop 훅은 종료 코드 2로 붙잡습니다. 이때 실패한 검사의 이름과 명령, 종료 코드를 알려 주고, run 명령의 출력은 앞 10줄만 돌려줍니다. 단계는 verify 그대로라서, AI는 문제를 고치고 11번(테스트)부터 다시 합니다. 붙잡힌 뒤 AI가 도구를 하나도 쓰지 않고 응답을 마쳐 같은 이유로 또 걸리면, Stop 훅은 턴을 끝내게 놓아줍니다. AI가 도구를 쓰며 고치는데도 같은 단계에서 10번 연속 붙잡히면, Stop 훅은 종료 코드 2 대신 종료 코드 0으로 끝나면서 메모를 내보냅니다. Claude Code는 이것을 훅 오류가 아니라 안내로 보여 주고, AI는 그 메모를 받아 한 번 더 응답합니다. 그 메모에는 붙잡힌 이유와 함께 사람에게 "계속 / 방법 바꾸기 / 그만두기"를 물으라는 지시가 들어 있습니다. 두 장치는 13절에서 자세히 설명합니다.
16. **마무리 단계로 넘김**: 검사가 모두 통과하면 Stop 훅이 `stage`를 verify에서 finish로 바꾸고, 일지에 검사별 종료 코드를 남깁니다. 그런 다음 하네스의 마무리 지시를 주며 붙잡습니다. 프로젝트가 `checks.json`의 마무리 단계 칸에 적어 둔 "위키에 기록하라"도 그 뒤에 함께 붙습니다.
17. **위키 쓰기**: AI가 이번 작업에서 사람과 정한 규칙(rule)이나 새로 알게 된 사실(fact)을 `docs/wiki/`에 쓰거나 고칩니다. 그다음 `wiki check`로 형식을 검사합니다. 커밋하기 전에 써야 같은 커밋에 들어갑니다.
18. **커밋과 push**: 지금 브랜치가 기본 브랜치면 AI가 먼저 새 브랜치를 만듭니다. 그다음 이번에 바꾼 파일만 하나씩 `git add`하고, 커밋한 뒤 push합니다. PR은 만들지 않습니다.
19. **보고**: AI가 일곱 항목으로 보고합니다(12절). "단계 기록" 항목에는 `task.history`를 Read로 열어 옮겨 적습니다. "위키" 항목에는 시작 커밋 이후 `docs/wiki/`에서 바뀐 파일을 적습니다.
20. **마지막 확인**: AI가 응답을 마치면 Stop 훅이 git 상태를 봅니다(12절). 걸리는 게 있으면 AI를 finish 단계에 붙잡아 둡니다. 없으면 `stage`를 done으로 바꾸고, 메모 없이 종료 코드 0으로 끝납니다. 그러면 턴도 그대로 끝납니다.
21. **사람 차례**: 사람이 보고를 읽고 PR을 만들지, 머지할지 정합니다. 20번까지 사람이 한 일은 요청, 모드·검사 고르기, 계획 승인 세 가지입니다. 이 밖에 사람이 답해야 하는 때도 있습니다. 요청이 위키 기록과 어긋날 때, 같은 단계에서 10번 연속 붙잡힐 때, 이번 일과 상관없는 변경이 남았을 때가 그런 예입니다. 끝난 뒤 "이것도 고쳐 줘"라고 하면 새 작업으로 시작합니다.

### 훅 스크립트 7개

4절에서 본 다섯 자리에 스크립트 일곱 개가 걸려 있습니다. 한 자리에 여러 개가 걸리기도 하고, `review-record.sh`처럼 한 스크립트가 두 자리에서 돌아가기도 합니다.

| 훅 스크립트 | 자리 | 하는 일 | 막는지 |
|---|---|---|---|
| `session-start.sh` | SessionStart | "코드 작업은 task 스킬로 시작하라"나 "지금 ○○ 단계다. 이어서 하려면 진도표를 같은 내용으로 다시 저장해 지시를 받으라"를 알림 | 안 막음 |
| `tool-count.sh` | PreToolUse (모든 도구) | `tool-seq` 파일에 도구를 쓴 횟수를 적음. Stop 훅이 같은 이유로 또 붙잡을지 정할 때, 그사이 AI가 도구를 썼는지 이 횟수로 봄(13절) | 안 막음 |
| `protect-generated.sh` | PreToolUse (Edit·Write·MultiEdit·NotebookEdit) | 자동 생성 파일을 고치려 하면 막음 | **막음** |
| `guard-state.sh` | PreToolUse (Edit·Write·MultiEdit·Bash) | 작업을 시작하거나 이어서 하거나 취소할 때만 진도표를 쓰게 하고 나머지는 막음 | **막음** |
| `stage-context.sh` | PostToolUse (Edit·Write·MultiEdit) | 진도표를 쓰면 시작 기록(작업 주인 세션, 작업을 시작할 때 있던 마지막 커밋 등)을 남기고, 단계 지시를 메모로 붙임 | 안 막음 |
| `review-record.sh` | PostToolUse (Read·SubagentHandback), SubagentStop | 리뷰어가 연 파일을 기록하고, 리뷰어가 끝나면 리뷰 통과 여부를 정해 `review.json`에 씀 | 안 막음 |
| `stop-gate.sh` | Stop | 검사의 run 명령을 실행하고 git을 확인함. 통과하면 단계를 넘기고 다음 지시를 주며 붙잡음. 통과하지 못하면 단계를 그대로 두고 붙잡음. 마무리 단계를 통과하면 done으로 바꾸고 놓아줌 | **붙잡음** |

표의 "자리" 열에서 괄호 안은 그 훅이 반응하는 도구입니다. MultiEdit는 예전 Claude Code에 있던 파일 고치기 도구입니다. 지금 도구 목록에는 없지만 훅 설정에 이름이 남아 있습니다. NotebookEdit는 Jupyter 노트북(코드와 실행 결과를 한 문서에 담는 `.ipynb` 파일)을 고치는 도구입니다. SubagentHandback은 auto 모드에서 서브에이전트가 일을 마치고 보고서를 넘길 때 쓰는 도구입니다(2절 도구 표). `review-record.sh`는 이때 리뷰어의 보고서를 받아 두었다가 리뷰 판정에 씁니다.

## 9절 · 통과는 프로그램이 판정해요

테스트와 빌드(2절)에 쓰는 명령은 프로젝트마다 다르고, 하네스는 그 명령을 모릅니다. 그래서 이 명령은 각 프로젝트의 `.harness/checks.json`에 검사로 적어 둡니다. 검사 하나는 아래처럼 칸(2절) 몇 개로 이루어집니다.

```json
{ "name": "unit-test",
  "description": "단위 테스트",
  "prompt": "scripts/harness/record unit-test npm test 로 테스트를 돌리고, 실패하면 고친다",
  "run": "scripts/harness/passed unit-test" }
```

### prompt 칸: 시키는 말

이 칸의 글은 검증 단계로 넘어갈 때 Stop 훅이 AI에게 줍니다. 1절의 프롬프트와 같은 단어지만, 여기서는 검사마다 붙여 두는 지시를 말합니다.

### run 칸: 확인하는 명령

Stop 훅이 프로젝트 루트에서 이 명령을 실행합니다. 종료 코드가 0이면 통과입니다. run이 비어 있으면 Stop 훅은 지시만 주고 확인하지 않습니다.

검사에는 보통 하네스 스크립트 두 개를 씁니다. prompt 칸에서 `record`로 검사를 돌리고, run 칸에서 `passed`로 그 결과를 봅니다. 두 스크립트가 하는 일과 판정 방식은 이렇습니다.

- <b>`record`</b>는 받은 명령을 대신 실행하고 결과를 두 파일에 남깁니다. `.harness/out/<이름>.json`에는 통과 여부와 종료 코드, 걸린 시간을 적습니다. `.harness/out/<이름>.log`에는 출력 전체를 적습니다. AI에게 돌려주는 출력은 성공이면 한 줄, 실패면 마지막 30줄뿐입니다. 긴 로그로 컨텍스트가 차지 않게 하려고 줄였습니다.
- <b>`passed`</b>는 그 결과가 통과였는지, 그리고 최신인지 봅니다. 통과였어도 다음 두 경우에는 최신이 아니라고 보고 실패로 칩니다. 첫째, 결과 파일이 이번 작업을 시작하기 전에 만들어졌을 때입니다. 둘째, 결과 파일을 만든 뒤에 이번 작업에서 바뀐 파일을 또 고쳤을 때입니다. 바뀐 파일은 git으로 찾기 때문에, 프로젝트가 git 저장소가 아니면 두 번째 확인은 건너뜁니다.
- 통과 여부는 종료 코드로 정하므로, AI가 보고에 "통과했어요"라고 써도 판정은 달라지지 않습니다.
- 다만 AI가 결과 파일을 고치면 판정이 바뀔 수 있는데, 하네스는 이것을 막지 않습니다(13절).
- 고른 검사만 돌립니다. 문구 한 줄을 고치는 일이라면 검사를 하나도 고르지 않아도 됩니다.

<a id="s10"></a>
## 10절 · 리뷰는 다른 AI가 하고, 훅이 기록해요

**코드 리뷰**는 코드를 쓴 사람이 아닌 다른 사람이 바뀐 코드를 읽고 문제를 찾는 일입니다. 하네스에서는 다른 AI가 리뷰를 합니다.

리뷰는 검증 단계에서 돌리는 검사 가운데 하나(`review`)라서, 작업 흐름 안에서는 사람이 골랐을 때만 합니다. 처음에 고르지 않았어도 작업하는 중에 "리뷰도 하자"라고 하면 더할 수 있습니다. 이와 별도로, 지침(`AGENTS.md`)에는 PR(12절)을 만들기 전에 리뷰어에게 검토를 맡기라는 말이 있습니다.

리뷰를 다른 AI에게 맡기는 방식은 이렇습니다.

- **메인 AI가 리뷰하지 않는 이유**: 자기가 쓴 코드는 후하게 보기 쉽습니다. 서브에이전트는 메인 AI의 대화를 모르니, 코드를 왜 이렇게 썼는지 듣지 못한 채로 읽습니다.
- **리뷰어가 쓸 수 있는 도구**: 리뷰어 설정에 적힌 도구 가운데 파일을 읽거나 명령을 실행하는 도구는 Read, Grep, Glob, Bash뿐입니다. Edit나 Write는 없지만, Bash로는 파일을 고칠 수 있습니다. 리뷰어의 지침에는 바뀐 내용을 git으로 볼 때만 Bash를 쓰고, 다른 파일에서 코드를 찾을 때는 Grep 도구를 쓰라고 적혀 있습니다. 그런데 macOS·Linux에서는 Grep 도구가 기본으로 없어서(2절), 지침과 실제로 쓸 수 있는 도구가 어긋납니다. 리뷰어가 Bash를 다른 데 써도 훅은 막지 않습니다.
- **무엇을 읽는지**: 리뷰어는 바뀐 파일을 모두 읽어야 합니다. 바뀐 테스트 파일도 여기에 들어가므로, 메인 AI가 테스트를 통과시키려고 조건을 느슨하게 바꿨다면 리뷰어가 찾아낼 수 있습니다. 리뷰어가 문제를 찾으면 메인 AI가 고치고 다시 리뷰를 맡깁니다.
- **파일을 열었는지 기록**: 8절 12번에서 본 대로, 리뷰어가 Read로 연 파일 이름은 `review-record.sh`가 `.harness/state/` 안에 적어 둡니다.
- **통과 판정**: 리뷰를 통과로 칠지는 8절 13번의 두 조건으로 정합니다. `review-record.sh`는 판정 결과를 `.harness/out/review.json`에 씁니다. 검사 review의 run 칸에 적힌 `passed review`가 이 파일을 읽습니다. 훅은 리뷰어가 바뀐 파일을 모두 열었는지 봐야 하는데, git 저장소가 아니면 바뀐 파일 목록을 만들 수 없습니다. 다른 검사는 이럴 때 두 번째 최신 확인만 건너뜁니다(9절). 리뷰는 다릅니다. `review-record.sh`가 결과 파일을 쓰지 않으므로 `passed review`가 실패합니다.

판정 결과 파일은 리뷰어가 끝날 때(`SubagentStop`)만 기록됩니다. 그래서 결과 파일이 있으면, 메인 AI가 그 파일을 직접 쓰거나 고치지 않은 한 리뷰어가 돌았다는 뜻입니다(13절). 다만 훅은 파일을 열었는지와 보고서의 줄만 보고, 지적이 맞는지는 보지 않습니다. 또 리뷰는 AI가 판단하므로 같은 코드라도 결과가 달라질 수 있습니다. 9절의 테스트 검사는 코드가 같으면 대개 결과도 같습니다.

<a id="s11"></a>
## 11절 · 위키에는 정한 것과 그 이유를 남겨요

코드만 봐서는 왜 그렇게 만들었는지 알 수 없습니다. 커밋 메시지에 이유를 적어 두어도, 나중에 그 커밋을 찾아 읽기는 어렵습니다.

**예**: 번역할 글은 한 번에 500자까지만 보내기로 정했습니다. 저사양 폰에서 앱이 멈췄기 때문입니다.

사람이 "500자에서 잘려요, 고쳐 줘"라고 하면, 이 이유를 모르는 AI는 버그로 보고 제한을 풀어 버릴 수 있습니다.

그래서 프로젝트의 `docs/wiki/` 폴더에 기록을 두고 git에 커밋합니다. 발표에서는 이것을 LLM Wiki라고 부릅니다. 기록은 두 종류입니다.

### rule · 규칙 기록

팀이 정한 규칙과 그 이유를 적는 기록입니다.

적는 항목은 규칙, 적용 범위, 근거, 예외입니다. 근거에는 기획서나 이슈의 주소와 날짜를 적습니다. 이슈는 할 일이나 버그를 적어 두는 게시판 글입니다.

### fact · 기술 기록

라이브러리와 플랫폼이 어떻게 동작하는지 확인한 사실을 적는 기록입니다.

적는 항목은 확인된 동작, 확인 방법, 함의, 안 다룬 것입니다. 함의에는 코드에서 조심할 점을 적습니다.

### 읽는 때와 쓰는 때

AI는 아래 세 경우에 위키를 다룹니다. 둘째는 어느 프로젝트에서나 합니다. 첫째와 셋째는 프로젝트가 위키 지시를 넣어 두었을 때만 합니다. 그 까닭은 아래에 적었습니다.

1. **시작할 때 읽기**: 계획 단계에서 `scripts/harness/wiki search 로그인`처럼 명령 뒤에 찾을 낱말을 넣어 검색하고, 나온 기록을 읽습니다. simple 모드라면 구현 단계를 시작할 때 읽습니다. 검색할 때마다 시각, 검색어, 찾은 개수가 `wiki-search.log`에 한 줄씩 남습니다. 나중에 사람이 이 로그를 보면 AI가 위키를 찾아봤는지 알 수 있습니다.
2. **바꾸기 전에 읽고, 어긋나면 묻기**: 동작을 바꾸기 전에는 관련 기록을 찾아 읽습니다. 요청이 기록과 어긋나면 AI는 바로 고치지 않고 "위키에는 이렇게 정해져 있어요. 바꿀까요?"라고 사람에게 묻습니다. 바꾸기로 하면 위키도 함께 고칩니다.
3. **마무리할 때 쓰기**: 커밋하기 전에 이번에 정한 것을 적습니다. 비슷한 기록이 이미 있으면 새로 만들지 않고 그 기록을 고칩니다. 다 쓰면 `scripts/harness/wiki check`로 형식을 검사합니다.

위키 지시는 이렇게 들어갑니다.

- 계획 단계에 위키를 찾고 마무리 단계에 기록하라는 단계별 지시는 하네스 코드에 넣지 않습니다. 위키를 쓰지 않는 프로젝트도 있기 때문입니다. 대신 프로젝트마다 `checks.json`의 `stages` 칸에 한 줄씩 적습니다. `stages`는 단계별로 지시를 덧붙이는 칸입니다.
- 이와 별개로, 동작을 바꾸기 전에 위키를 찾아 읽고 기록과 어긋나면 사람에게 물으라는 규칙은 하네스 지침(`AGENTS.md`)에 늘 들어 있습니다.
- `setup`은 프로젝트 설정을 정할 때 AI가 실행하는 스크립트로, 사람에게 무엇을 물을지 안내를 출력합니다. 하네스 0.14.1부터는 위키 지시를 `stages`에 넣을지 묻는 항목이 이 안내에 더해졌습니다. 지시가 빠져 있으면 점검 스크립트 `doctor`가 알려 줍니다(둘 다 14절).

위키는 훅이 확인하지 않습니다. 발표 팀도 위키는 지시 한 줄로만 다뤘습니다. 위키를 쓰라고 강제하면, 새로 정한 것이 없는 일에서도 AI가 억지로 기록을 만들 수 있습니다. 무엇을 썼는지는 사람이 마무리 보고(12절)의 "위키" 항목에서 봅니다.

2026-11-09 기준으로 시험장 세 곳 가운데 ReadSharp(영어 공부 앱)에는 기록이 24개, IntervalTimer(운동 타이머 앱)에는 14개 있습니다. PetCycle(반려동물 앱)에는 아직 기록이 없습니다. 위키 지시가 빠져 있었기 때문입니다. 이를 확인한 뒤 PetCycle의 `checks.json`에도 위키 지시를 넣었습니다.

## 12절 · 커밋하고 push해야 끝나요

여기서는 git 용어가 몇 개 더 나옵니다.

- **브랜치 (branch)**: 작업을 나눠 하는 갈래입니다. 중심이 되는 브랜치를 기본 브랜치(`main`, `develop` 등)라고 하고, 새 일은 보통 새 브랜치에서 합니다. 기본 브랜치에 바로 커밋하면 아무도 검토하지 않은 변경이 중심 갈래에 들어갑니다.
- **push · 원격 (remote)**: 내 컴퓨터의 커밋을 GitHub 같은 서버에 올리는 것을 push라고 하고, 그 서버를 원격이라고 합니다. 원격에 올려야 다른 사람이 볼 수 있습니다. 내 브랜치와 연결된 원격의 브랜치는 upstream이라고 합니다.
- **PR · 머지 (pull request · merge)**: PR은 내 브랜치를 기본 브랜치에 합쳐 달라는 요청입니다. 머지는 두 브랜치를 실제로 합치는 일입니다.
- **`git add`**: 이번 커밋에 넣을 파일을 고르는 명령입니다. `git add .`처럼 점을 붙여 쓰면 지금 폴더 아래에서 바뀐 파일을 모두 넣기 때문에, 넣으면 안 되는 파일이 섞일 수 있습니다.

### 마무리 단계에서 AI가 하는 일

1. 프로젝트가 마무리 단계에 정해 둔 지시(예: 위키 기록)가 있으면 그것부터 따릅니다.
2. 지금 브랜치가 기본 브랜치면 새 브랜치를 만듭니다.
3. 이번에 바꾼 파일만 하나씩 `git add`합니다. 비밀 정보나 이번 일과 상관없는 변경은 넣지 않습니다.
4. 커밋하고 push합니다. PR을 올릴지, 머지할지는 사람이 정합니다.
5. 일곱 항목으로 보고합니다.
   - 상황: 무엇을 끝냈고 무엇이 남았는지
   - 조치: 바꾼 파일과 바꾼 내용
   - 평가: 검사별 통과 여부와 근거
   - 단계 기록: 훅이 남긴 일지
   - 위키: 이번에 쓰거나 고친 기록
   - 건의: 사람이 결정하거나 직접 처리해야 할 일
   - 결정 사항: 코드에 남지 않는 결정과 그 이유

"단계 기록" 항목은 AI가 기억으로 채우지 않습니다. 훅이 적어 둔 일지 `task.history`를 읽어 옮겨 적습니다. 옮기다 틀릴 수도 있으므로, 의심되면 사람이 그 파일을 열어 보고서의 단계 기록과 대조합니다.

### Stop 훅이 git으로 확인하는 것

- 작업을 시작할 때 없던 변경이 커밋되지 않고 남았나? 시작할 때 이미 바뀌어 있던 파일은 훅이 `task.wip`에 적어 두고 확인에서 뺍니다. 다른 사람이 하던 작업일 수 있어서입니다.
- 기본 브랜치에 커밋했나?
- upstream이 없나?
- push하지 않은 커밋이 남았나?
- 어느 브랜치에도 속하지 않은 상태(detached HEAD)에서 커밋했나?

하나라도 걸리면 Stop 훅은 AI를 마무리 단계에 붙잡아 둡니다. 작업하는 동안 이번 일과 상관없는 변경이 새로 생겼다면 그 변경이 남아 있는 한 계속 걸립니다. 이럴 때 AI는 그 변경을 커밋하지 않고, 작업 보고의 건의 항목에 적어 어떻게 할지 사람에게 묻습니다. 질문 창을 띄우지 않고 보고 글로 묻는 것이라, AI는 도구를 쓰지 않고 응답을 마칩니다. 이렇게 응답을 마쳤는데 같은 이유로 또 걸리면 훅이 놓아줍니다. AI가 도구를 쓰는데도 10번 연속 걸리면 훅은 사람에게 넘깁니다(둘 다 13절).

기본 브랜치에 커밋했을 때도 훅은 push하지 말고 사람에게 알리라며 붙잡고, 같은 방식으로 놓아줍니다.

확인을 건너뛰는 경우도 있습니다. git 저장소가 아니거나 시작 커밋(`task.base`)이 없으면 아무것도 확인하지 않습니다. 원격이 없거나, 이번 작업에서 새 커밋이 하나도 없으면 첫째 항목(커밋하지 않은 변경)만 확인하고 브랜치와 push는 보지 않습니다.

### 사람이 PR을 만들라고 하면

PR은 사람이 만들라고 하거나 AI가 물어 사람이 허락할 때만 만듭니다. 이때 AI는 지침(`AGENTS.md`)대로 `scripts/harness/pr-video`를 실행합니다. 이번 작업에서 E2E 영상을 찍었다면, 이 스크립트가 그 영상을 GitHub에 올릴 수 있는 크기로 줄입니다. 찍은 영상이 없으면 아무 일도 하지 않습니다.

AI는 줄인 영상을 Chrome으로 PR 페이지에 올리고, 받은 링크를 PR 본문에 넣습니다. 리뷰어는 앱을 실행하지 않고 PR 화면에서 바로 영상을 봅니다. 고치기 전 영상도 남겨 두는 프로젝트라면 두 영상이 함께 들어갑니다. 브라우저를 쓰는 까닭은 GitHub가 웹 화면에서 올린 영상만 본문에서 재생해 주기 때문입니다. Chrome을 쓸 수 없으면 AI가 영상 파일 위치를 알려 주고, 사람이 PR에 끌어다 놓습니다.

## 13절 · 훅은 스스로 물러서기도 하고, 못 막는 것도 있어요

### 훅이 지나치게 막지 않게 하는 장치

#### 같은 이유로 되풀이되면 놓아주기

Stop 훅이 붙잡았는데, AI가 도구를 하나도 쓰지 않고 응답을 마쳐 같은 이유로 또 걸릴 때가 있습니다. 이때 Stop 훅은 턴을 끝내게 놓아줍니다. 훅과 AI가 같은 말만 계속 주고받지 않게 하려는 장치입니다. 도구를 쓸 때마다 PreToolUse 훅 `tool-count.sh`가 `tool-seq` 파일에 횟수를 적고, Stop 훅은 이 횟수로 AI가 도구를 썼는지 압니다. 놓아줘도 통과한 것은 아니어서 단계는 그대로입니다. 일지에는 "release"로 남습니다. 사람이 다음에 말을 걸고 AI가 다시 응답을 마치면 그때 또 확인합니다. 단계를 연달아 넘길 때처럼 붙잡는 이유가 매번 다르면 Stop 훅은 놓아주지 않습니다. 이럴 때는 Claude Code 자체의 상한이 걸립니다. AI가 도구를 쓰지 않은 채 8번 연속 붙잡히면, Claude Code는 그다음 붙잡기를 무시하고 턴을 끝냅니다.

#### 10번 연속 붙잡히면 사람에게 넘기기

AI가 도구를 쓰며 고치는데도 같은 단계에서 10번 연속 붙잡히면, Stop 훅은 검사 실패든 커밋·push 문제든 종료 코드 2로 끝내지 않습니다. 대신 종료 코드 0으로 끝내면서 메모를 내보냅니다. 메모에는 막힌 이유와, 사람에게 "계속 / 방법 바꾸기 / 그만두기"를 물으라는 지시가 들어 있습니다. 0으로 끝나도 메모는 AI에게 전해지므로(4절), AI는 한 번 더 응답하며 사람에게 묻습니다. 횟수는 이때 처음부터 다시 셉니다.

#### 서브에이전트를 기다리는 동안은 확인 안 하기

리뷰어 같은 서브에이전트가 메인 AI와 따로 돌고 있으면(백그라운드 실행), Stop 훅은 붙잡지도 않고 단계를 넘기지도 않습니다. 서브에이전트가 끝난 뒤 AI가 응답을 마치면 다시 확인합니다.

#### 진도표를 마지막으로 쓴 세션만 감독하기

진도표를 마지막으로 쓴 세션이 작업 주인(`task.owner`)이 되고, Stop 훅은 주인 세션만 확인합니다. 같은 프로젝트에 다른 세션을 새로 열어도, Stop 훅은 그 새 세션을 붙잡지 않습니다. 다만 새 세션에서 "이어서 하기"로 진도표를 다시 저장하면, 그때부터는 새 세션이 주인입니다.

#### 설정이 없으면 끼어들지 않기

`.harness/project.json`이 없는 프로젝트에서는 훅이 확인을 하지 않습니다. 하네스를 깔지 않은 프로젝트까지 막으면 안 되기 때문입니다. Bash로 진도표를 쓰는 명령만은 이 파일이 없어도 막는데, 하네스를 깔지 않은 프로젝트에서는 그런 명령을 쓸 일이 없어 상관없습니다. 다만 검사를 골라 작업을 시작한 뒤 `checks.json`만 지워지거나 깨지면 다릅니다. 이때 Stop 훅은 검증 단계에서 오히려 단계를 넘기지 않고 붙잡습니다.

### 처음부터 막는 것

하네스가 막는 자동 생성 파일은 setup 때 `project.json`의 `generated`에 적어 둔 파일입니다. iOS 프로젝트 설정 프로그램 Tuist가 만든 파일이 그 예입니다. AI가 이런 파일을 Edit나 Write로 고치려 하면 PreToolUse 훅 `protect-generated.sh`가 막고, 파일을 만드는 쪽을 고치라고 알려 줍니다. 비밀 파일은 훅이 아니라 권한 `deny`로 읽지 못하게 합니다(2절).

### 하네스가 못 막는 것

아래는 지금 하네스에 남아 있는 빈틈입니다.

- **작업을 시작하지 않으면 감독하지 않습니다.** 진도표가 없으면 Stop 훅은 확인하지 않습니다. 세션을 열 때 SessionStart 훅이 "코드 작업은 task 스킬로 시작하라"라고 알려 줄 뿐입니다.
- **하네스가 쓰는 파일 가운데 진도표만 지킵니다.** AI가 `.harness/out/unit-test.json`이나 `.harness/out/review.json`에 통과라고 써넣으면 `passed`는 통과로 봅니다. 일지 `task.history`와 작업 주인 `task.owner`도 지키지 않습니다. `task.owner`를 지우면 Stop 훅은 그 작업을 감독하지 않습니다.
- <b>`guard-state.sh`는 Bash 명령에 적힌 글자만 봅니다.</b> 정해 둔 쓰기 명령에 없는 프로그램을 쓰거나, 변수로 파일 이름을 감추면 잡지 못합니다. 막는 것은 아래 세 가지에 모두 맞는 명령뿐입니다.
  - 명령에 `task.json`이라는 글자가 들어 있다.
  - 명령이나 명령을 실행하는 폴더 경로에 `.harness/state`라는 글자가 들어 있다.
  - `>`, `cp`, `mv`, `rm`, `sed -i`, `python`처럼 정해 둔 쓰기 명령이 있다.
- **자동 생성 파일을 Bash로 고치면 잡지 못합니다.** `protect-generated.sh`는 Edit, Write 같은 파일 도구만 봅니다.
- **비밀 파일 막기에도 빈틈이 있습니다.** 권한 규칙은 목록에 적은 이름만 막습니다(2절). 목록에 있는 파일이라도 AI가 python 같은 프로그램으로 열거나, 파일 이름을 적지 않고 폴더 전체를 검색하면 읽힐 수 있습니다.
- **하네스가 기대는 설정은 AI도 고칠 수 있습니다.** `checks.json`의 run 칸, `project.json`, 플러그인을 켜는 `.claude/settings.json`을 고치거나 지워도 하네스 훅은 막지 않습니다. Claude Code 쪽에서는 `.claude` 폴더에 쓸 때 따로 확인을 받습니다. 그래서 `.claude/settings.json`은 대개 사람이나 auto 모드의 판정기가 한 번 더 봅니다. 사람이 모든 확인을 건너뛰는 모드(bypassPermissions)를 켜 두었다면 이 확인도 없습니다. 이런 변경은 커밋에 남으므로 사람이 커밋 기록이나 PR에서 볼 수 있습니다.
- **계획 승인과 구현 단계는 확인하지 않습니다.** 승인을 받지 않고 응답을 마쳐도 다음 단계로 넘어갑니다(7절).
- **시작 전에 바뀌어 있던 파일은 확인에서 빠집니다.** AI가 이번 작업에서 그 파일을 또 고치고 커밋하지 않아도 잡지 못합니다. `task.wip`은 파일 이름만 적어 두기 때문입니다.
- **오류 출력에 파일이 없다는 말이 있으면 붙잡지 못합니다.** Claude Code는 Stop 훅이 종료 코드 2로 끝나도, 오류 출력에 "No such file or directory" 같은 말이 있으면 붙잡지 않고 턴을 끝냅니다. run 명령이 가리키는 파일이 없거나 검사 출력에 그런 말이 섞이면 여기에 해당합니다. 단계는 검증 단계(verify) 그대로 남지만 AI는 붙잡히지 않습니다. run 명령이 가리키는 파일이 없는 경우는 `doctor`가 알려 줍니다.
- **jq가 없으면 훅이 사실상 꺼집니다.** 훅은 JSON을 읽을 때 jq라는 프로그램을 씁니다. jq가 설치되지 않은 컴퓨터에서는 훅이 아무것도 확인하지 못하고 모든 요청을 그냥 통과시킵니다. AI가 진도표를 쓸 때마다 훅이 jq가 없다고 알려 줄 뿐입니다. jq 설치 여부는 `doctor`로 점검할 수 있습니다.

검사 결과 파일, 일지와 작업 주인 파일, `.claude/settings.json`을 막을지는 하네스를 만드는 사람이 정합니다. 이 일은 하네스 저장소의 작업 계획표(`docs/roadmap.md`)에 검토할 거리로 올려 두었습니다. 참고로 ai-bouncer는 자기 상태 파일과 설정 파일을 Write나 Edit로 고치는 것을 막습니다. 위에 적은 나머지 빈틈은 AI가 그 틈에서 실수하는지 시험장에서 지켜본 뒤 정합니다. 실수를 본 뒤에 훅을 더한다는 원칙(16절)을 따릅니다.

<a id="s14"></a>
## 14절 · 프로젝트에 까는 방법

| 명령 | 실행 위치 | 하는 일 |
|---|---|---|
| `scripts/init <프로젝트 경로>` | 하네스 저장소 | 프로젝트에 하네스를 처음 깝니다. `template`의 파일을 복사하고, `.claude/settings.json`에 플러그인을 켜는 줄과 플러그인을 받아 올 곳을 적습니다. |
| `scripts/sync <프로젝트 경로>` | 하네스 저장소 | 프로젝트에 복사해 둔 template 파일을 새 버전으로 갱신합니다. 하네스가 관리하는 부분만 바꾸고, 프로젝트 쪽에서 적은 부분은 그대로 둡니다. 예를 들어 `AGENTS.md`에서는 하네스 영역으로 표시해 둔 곳만 고칩니다. |
| `scripts/harness/setup` | 프로젝트 | 프로젝트마다 정할 설정을 묻는 안내를 출력합니다. 프로젝트 저장소에서 찾은 단서도 함께 보여 줍니다. AI는 이 안내를 보고 사람에게 묻고, 받은 답으로 설정 파일을 씁니다. 정할 것: 검사 목록, 자동 생성 파일, 권한 규칙으로 편집을 막을 파일, 위키 지시, 빌드·테스트 명령 |
| `scripts/harness/doctor` | 프로젝트 | 하네스가 잘 깔렸는지 점검합니다. 점검 항목: 플러그인 버전이 맞는지, jq가 깔려 있는지, `CLAUDE.md`에 `@AGENTS.md` 줄이 있는지, 검사 목록의 run 명령을 실행할 수 있는지, 위키 지시가 있는지 |

하네스에는 특정 플랫폼(iOS, 웹, 안드로이드 등)에 맞춘 내용이 없습니다. 무엇으로 빌드하고 테스트할지는 사람이 정합니다.

하네스를 깐 프로젝트를 처음 열면 "이 폴더를 믿을지" 묻는 창이 뜹니다. 허용하면 Claude Code가 `init`이 적어 둔 곳에서 플러그인을 받아 와 켭니다. 플러그인을 설치할지는 따로 묻지 않습니다. 플러그인에 든 MCP 서버(`harness-network`)도 함께 켜집니다. 이 서버의 도구에도 다른 도구처럼 권한 규칙이 적용됩니다. 그래서 Claude Code가 실행 전에 사람에게 물을 수 있습니다.

플러그인이 켜졌는지 확인하려면 Claude Code 입력창에 `/plugin`을 입력해 목록을 봅니다. 목록에 없으면 터미널에서 아래 명령 두 개를 차례로 실행합니다. 첫 줄은 플러그인 배포 목록(마켓플레이스)을 등록하고, 둘째 줄은 플러그인을 설치합니다. `--scope project`는 이 프로젝트에서 쓰도록 설치한다는 뜻입니다.

```bash
claude plugin marketplace add Gooreum/ai-harness
claude plugin install harness@ai-harness --scope project
```

플러그인(훅, 스킬, 리뷰어)은 `sync`로 바뀌지 않습니다. 플러그인은 이 마켓플레이스에서 받아 오므로, 아래 명령으로 목록을 새로 받은 뒤 플러그인을 업데이트합니다.

```bash
claude plugin marketplace update ai-harness
claude plugin update harness@ai-harness
```
 업데이트한 뒤에는 열려 있는 세션에서 `/reload-plugins`를 실행하거나 세션을 새로 열어야 새 훅이 적용됩니다.

<a id="s15"></a>
## 15절 · 처음 쓰면 이런 걸 많이 물어요

**Q. 단계는 저절로 넘어가?**

AI가 응답을 마칠 때 Stop 훅이 넘깁니다. 계획 단계와 구현 단계는 따로 볼 조건이 없어서, 일을 다 못 했어도 응답을 마치면 넘어갑니다. 검증 단계는 고른 검사를 모두 통과해야 넘어가고, 마무리 단계에서는 커밋과 push를 마쳐야 작업이 끝납니다(예외는 12절).

**Q. AI가 진도표를 고쳐서 단계를 넘겨?**

아니요. 단계는 Stop 훅이 넘깁니다. AI는 작업을 시작할 때, 이어서 할 때, 취소할 때만 진도표를 쓸 수 있습니다. 단계를 넘기려고 Write나 Edit, 정해 둔 Bash 명령으로 쓰면 `guard-state.sh`가 막습니다. 빈틈은 13절에 있습니다.

**Q. PostToolUse 훅이 모든 작업을 기록해?**

아니요. PostToolUse 훅은 정해 둔 도구(Edit, Write, Read 등)를 AI가 쓸 때마다 돌지만, 하는 일은 둘뿐입니다. 하나는 진도표를 저장할 때 하는 일로, 시작 커밋 같은 작업 시작 정보를 남기고(8절 5번) 지금 단계의 지시를 붙입니다. 다른 하나는 리뷰어가 연 파일 이름과 넘긴 보고서를 기록하는 일입니다. 그 밖에는 아무것도 하지 않습니다. 검사를 통과했는지, 커밋했는지는 Stop 훅이 확인합니다.

**Q. 훅은 AI가 불러야 돌아?**

아니요. Claude Code가 정해진 순간에 부릅니다.

**Q. 리뷰는 언제 해?**

작업 흐름 안에서는 사람이 리뷰를 골랐을 때 검증 단계에서 합니다. 사람이 PR을 만들라고 하면, AI는 지침에 따라 그 전에 리뷰어에게 맡기기도 합니다(10절).

**Q. 위키를 빼먹으면 붙잡혀?**

붙잡히지 않습니다. 위키는 지시로만 다루고 훅은 확인하지 않습니다(11절). 무엇을 썼는지는 사람이 보고의 "위키" 항목에서 봅니다.

**Q. 작업을 시작하지 않고 그냥 "고쳐 줘" 하면?**

진도표가 없으니 Stop 훅은 확인하지 않습니다(13절). 사람이 task 스킬을 부르는 명령 `/harness:task`를 입력해 AI가 작업을 시작하게 할 수 있습니다.

**Q. 작업이 끝난 뒤 "이것도 고쳐 줘" 하면?**

끝난 작업에 이어 붙이지 않고 새 작업으로 시작합니다. 모드와 검사도 다시 고릅니다.

**Q. 작업을 그만두고 싶으면?**

"그만하자"라고 말하면 AI가 진도표를 취소 상태로 바꾸고 어디까지 했는지 보고합니다. 사람이 말하지 않았는데 AI가 스스로 그만두지 않도록 지시해 두었습니다.

<a id="s16"></a>
## 16절 · 발표를 따르고, 발표에 없는 것은 ai-bouncer를 따라요

하네스를 만들 때 따른 기준과, 장치를 넣고 뺀 경위입니다.

- **1순위는 발표 "Workflow AX 적용기"입니다.** 발표에서 가져온 원칙은 넷입니다.
  - 검사 목록은 설정 파일에 둔다.
  - 돌릴 검사는 사람이 고른다.
  - 통과는 프로그램이 판정한다.
  - 팀의 규칙과 그 이유는 위키에 남긴다.
- **2순위는 ai-bouncer입니다.** 발표에 없는 동작은 ai-bouncer를 따릅니다. 코드를 가져다 쓰지는 않고, 어떻게 동작하는지만 참고합니다.
- 발표나 ai-bouncer와 다르게 만들 때는 사람이 정하고, 그 이유를 설계 결정 기록에 남깁니다. 설계 결정 기록은 ADR(Architecture Decision Record)이라고도 부릅니다. 하네스 저장소의 `docs/decisions/`에 0028번까지 있습니다.
- 처음에는 위험하거나 되돌리기 어려운 행동 세 가지만 다뤘습니다. 자동 생성 파일 고치기와 비밀 파일 읽기는 훅과 권한으로 막았고, 지금도 막고 있습니다(빈틈은 13절). 이력을 지우거나 밖으로 공개하는 git 작업은 할 때마다 사람에게 묻게(`ask`) 했고, 그 뒤 배포 명령도 묻는 목록에 더했습니다.
- git과 배포 명령을 묻는 규칙은 나중에 모두 뺐습니다. 확인 창이 너무 자주 떠서 시험장을 쓰는 사람이 그렇게 정했습니다(ADR 0026). git 명령은 이제 지침(`AGENTS.md`)과 auto 모드의 판정기(2절 끝)에 맡기고, 배포 명령은 판정기에만 맡깁니다. auto 모드가 아니면 Claude Code가 사람이 정해 둔 권한 설정에 따라 사람에게 묻거나 바로 실행합니다.
- 나머지 장치는 시험장에서 실수를 본 뒤에 넣습니다. 예를 들어 AI가 Bash로 진도표를 쓴 일을 두 번 봤을 때는 훅을 늘리지 않고, task 스킬에 Write로 쓰라는 한 줄만 보탰습니다. 그 뒤 단계 넘기기를 Stop 훅으로 옮기면서, `guard-state.sh`가 Bash로 진도표를 쓰는 것도 막게 했습니다(7절). 커밋과 push 확인은 예외입니다. 발표 팀은 하네스를 처음 만들기 전에는 지침 파일에 커밋하라고 적어 둬도 AI가 커밋을 빠뜨렸다고 했습니다(슬라이드 5). 그래서 이 확인은 시험장에서 실수를 보기 전에, 하네스 0.14.0에서 넣었습니다.

아래 표에서 발표, ai-bouncer, 이 하네스를 견줘 봅니다. 발표 팀은 하네스를 두 번 만들었습니다. 표에 나오는 "첫 하네스"는 처음 만든 것입니다. 발표 열은 발표에서 마지막으로 소개한 방식을 기준으로 적었고, 첫 하네스가 그와 다른 행에는 첫 하네스의 내용을 괄호 안에 적었습니다.

|  | 발표 | ai-bouncer | 이 하네스 |
|---|---|---|---|
| 단계를 넘기는 쪽 | AI가 진도표에 직접 적음 | Stop 훅 | Stop 훅 (발표와 달리 ai-bouncer를 따름, 7절) |
| 모드를 고르는 쪽 | 사람 (첫 하네스는 늘 계획부터) | 설정에 따라 사람이나 AI | 사람 |
| 진도표를 만드는 쪽 | AI | AI (`bouncer start` 명령으로) | AI (Write로 씀, 훅이 확인) |
| 진도표를 고치려 할 때 | 다루지 않음 | Write, Edit만 막음 | 정해 둔 Bash 명령까지 막음 |
| 리뷰 | 다루지 않음 (첫 하네스는 마지막에 품질 확인 에이전트가 결과물을 검토) | 메인 AI가 다시 읽음, 훅은 확인하지 않음 | 리뷰어 서브에이전트가 읽음, 훅이 기록 |
| 마무리 커밋 | 마무리 단계에서 커밋하지 않음 (첫 하네스는 구현을 작은 단위로 나눠 단위마다 커밋) | 지시만 함 | Stop 훅이 git으로 확인 |
| 위키 | 지시 한 줄 | 없음 | 지침의 규칙과 stages 지시 (강제하지 않음) |

---

**요약**: AI는 도구를 요청만 하고 실행은 Claude Code가 하므로, 그 앞뒤에 훅이 끼어들 수 있습니다. AI는 작업을 시작할 때, 이어서 할 때, 취소할 때만 진도표를 씁니다. 단계는 AI가 응답을 마칠 때 Stop 훅이 검사 결과와 git 상태를 보고 넘깁니다. 확인에 걸리면 Stop 훅이 AI를 붙잡습니다. 어떤 검사를 돌릴지는 사람이 고릅니다. AI는 동작을 바꾸기 전에 위키를 찾아 읽습니다. 프로젝트가 위키 지시를 넣어 두면, 작업을 마칠 때 정한 것과 그 이유를 위키에 남깁니다. 하네스가 못 막는 것은 13절에 있습니다.
