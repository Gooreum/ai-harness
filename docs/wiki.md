# 정책·결정 기록 (`docs/wiki/`)

코드와 커밋에 남지 않는 "왜"를 모아 두는 곳이다. 각 프로젝트의 `docs/wiki/`에 두고 git에 커밋한다.
발표의 LLM Wiki를 프로젝트 안 파일과 검색 스크립트로 시작한 것이다([ADR 0008](decisions/0008-wiki.md)).

## 언제 쓰고 언제 읽나

| 때 | 누가 | 무엇을 |
|---|---|---|
| 작업 시작 (plan 단계, simple이면 implement 단계 처음) | 에이전트 | `scripts/harness/wiki search <단어>`로 관련 기록을 찾아 읽는다 |
| 기록과 반대되는 요청 | 에이전트 → 사람 | 바로 고치지 않고 기록과 근거를 보여 주며 정책을 유지할지 묻는다 |
| 작업 마무리 (finish 단계) | 에이전트 | 이번에 정한 결정·알게 된 사실을 쓴다. 비슷한 기록이 있으면 고친다 |

- 언제 찾고 쓰라는 지시는 하네스 코드가 아니라 프로젝트의 `.harness/checks.json`의 `stages.<단계>.prompt`에 한 줄씩 둔다. 발표에서도 마무리 단계에 config 한 줄을 더했다.
- 템플릿 규칙 `.claude/rules/harness/wiki.md`가 `docs/wiki/`의 파일을 열 때 함께 읽혀 형식과 절차를 알려 준다.

## 두 종류

| `kind` | 무엇 | 항목 |
|---|---|---|
| `fact` (기술 기록) | 라이브러리·플랫폼이 실제로 어떻게 동작하는지. 다른 팀에서도 맞는 사실 | 확인된 동작, 확인 방법, 함의, 안 다룬 것 |
| `rule` (결정 기록) | 이 서비스·팀이 정한 규칙과 이유 | 규칙, 적용 범위, 근거(기획서·이슈·Slack 주소와 날짜), 예외 |

경로는 `docs/wiki/<주제>/<영문-소문자-하이픈>.md`다. 머리말에 `kind`와 `tags: [..]`를, 본문 첫 제목에 한 줄 요약을 쓴다.

```markdown
---
kind: rule
tags: [번역, 글자수]
---

# 온디바이스 번역은 한 번에 500자까지만 보낸다

## 규칙
## 적용 범위
## 근거
## 예외
```

## 스크립트

```bash
scripts/harness/wiki search 번역 500   # 모든 단어가 든 기록: "종류  경로  제목"
scripts/harness/wiki check             # 모든 기록의 형식 검사
scripts/harness/wiki check docs/wiki/translation/x.md
```

- search는 대소문자를 무시하고 모든 단어가 들어 있는 기록을 찾는다. 찾으면 0, 없으면 1로 끝난다.
- 검색마다 `.harness/state/wiki-search.log`에 시각·검색어·결과 수를 남긴다. 발표처럼 "검색 → 열람 → 반영"을 재려면 이 기록부터 쓴다. 열람·반영은 아직 재지 않는다.
- check는 머리말, `kind`, `tags`, 제목, 종류별 항목을 본다. 문제가 있으면 파일마다 출력하고 1로 끝난다.
- check는 git이 무시하는 기록도 문제로 본다. 기록은 저장소에 올려야 다음 작업에서 찾을 수 있다(발표 슬라이드 46). iOS `.gitignore`의 `build/` 같은 규칙에 폴더 이름이 걸리기 쉽다.
