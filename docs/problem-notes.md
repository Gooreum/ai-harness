iOS AI 코딩 하네스(ios-ai-harness)를 시험장에서 돌리며 만난 문제와, 하네스를 만들며 물었던 질문과 답을 모은다.
경력기술서에 옮길 수 있게 문제마다 한 줄 요약을 둔다.

- 하네스: AI 에이전트가 정해진 단계(계획 → 구현 → 검증 → 마무리)를 지키게 하는 훅·스크립트·지침 묶음. 여기어때 안드로이드 팀 발표(DroidKnights 2026)와 발표자의 ai-bouncer를 기준으로 만든다.
- 시험장: ReadSharp, IntervalTimer 앱의 별도 워크트리.
- 자세한 관찰 기록은 [harness-log.md](harness-log.md), 설계 결정은 [decisions/](decisions/)에 있다.

## 1. 상태 파일을 Bash로 써서 단계 지시가 주입되지 않았다

**한 줄 요약:** 에이전트가 상태 파일을 훅이 감시하지 않는 도구(Bash)로 쓴 문제를 해결했다. 훅을 늘리지 않고, 스킬 지침 한 줄로 해결했다.

### 기술 설명

**배경: 단계 지시가 들어가는 구조**

- 작업 진행 상태는 `.harness/state/task.json`에 적는다. `stage` 값은 `plan` → `implement` → `verify` → `finish` → `done` 순으로 바뀐다.
- 플러그인 훅 두 개가 `task.json`의 편집에 걸려 있다. `hooks.json`의 matcher는 `Edit|Write|MultiEdit`다.
  - PreToolUse `check-run.sh`: verify를 지나 넘어가려 하면 고른 검사의 `run`을 돌린다. 실패하면 편집을 막는다(exit 2).
  - PostToolUse `stage-context.sh`
    - 바뀐 단계의 지시(`.harness/checks.json`의 prompt)를 `additionalContext`로 넣는다.
    - 작업 주인 세션을 `.harness/state/task.owner`에 적는다.
- 발표 슬라이드 27과 같은 구조다. "AI가 state.json의 단계를 고쳐 적는 순간 PostToolUse 훅이 지시를 넣는다."

**문제**

- IntervalTimer #8을 시작할 때 일어났다. 에이전트가 `task.json`을 `cat > .harness/state/task.json <<'EOF' … EOF`(Bash heredoc)로 만들었다.
- Bash는 matcher에 없어서 두 훅이 모두 돌지 않았다. 그래서 세 가지가 빠졌다.
  - 첫 단계 지시가 주입되지 않았다.
  - `task.owner`가 이 세션으로 바뀌지 않았다. Stop 게이트(`stop-gate.sh`)와 도구 수 세기(`tool-count.sh`)도 이 세션을 작업 주인으로 보지 않았다.
  - verify 이후로 넘어갈 때 Bash로 썼다면 검사 강제(`check-run.sh`)도 건너뛸 수 있었다.
- ReadSharp 세션 `8e3ca645`에서도 같은 일이 한 번 있었다(두 번째 관찰).
- 두 번 모두 에이전트가 곧바로 같은 내용을 Read → Write로 다시 저장해 지시를 받았다. 이후 단계 전환은 모두 Edit로 했다.

**원인** (계층: Context)

- task 스킬(`plugin/skills/task/SKILL.md`)에는 "`task.json`을 쓴다"만 있었다. 어떤 도구로 쓰는지는 없었다.
- Claude Code auto 모드의 기본 안내는 작은 파일 수정을 Bash(heredoc·sed)로 해도 된다고 한다.
- 에이전트가 훅을 우회하려던 것이 아니다. Write·Edit로 써야 훅이 돈다는 것을 몰랐다.

**해결**

- task 스킬의 "시작"과 "이후" 두 곳에 한 줄씩 넣었다. 내용은 "`task.json`은 Write·Edit로 쓴다. Bash로 쓰면 훅이 돌지 않아 단계 지시가 들어오지 않는다"이다.
- 검토하고 쓰지 않은 방법

| 방법 | 장점 | 쓰지 않은 이유 |
| --- | --- | --- |
| PreToolUse(Bash) 훅으로 명령에 `task.json` 경로가 있으면 막기 | 관찰된 두 경우를 확실히 막는다 | 지침 한 줄로 고칠 실수다. 모든 Bash 호출에 훅이 하나 더 돈다. 원칙 "강제 장치는 필요가 확인된 뒤에"에 따랐다 |
| `task.json` 지문(해시)을 저장해 두고 훅 밖에서 바뀐 것을 감지하기 | 변수 경로, 스크립트, MCP 도구, 사람이 직접 고친 경우까지 잡는다 | 이런 경로는 일부러 돌아가야 생긴다. 관찰된 적도 없다 |
| ai-bouncer처럼 엔진(Stop 훅)이 단계를 넘기고 에이전트는 상태 파일을 못 쓰게 하기 | 에이전트가 상태 파일을 쓸 일이 없어진다 | 발표 구조(슬라이드 14·27)에서 벗어나고 고칠 곳이 크다. ai-bouncer도 상태 파일 보호는 Edit·Write·MultiEdit·NotebookEdit에만 건다 |

- 재발 기준: 지침을 넣은 뒤에도 Bash로 쓰는 일이 다시 관찰되면 PreToolUse(Bash) 훅을 검토한다.
- 커밋: `22a1eaf`

**결과:** 고친 뒤 IntervalTimer에서 두 번 돌려 봤고, 두 번 모두 상태 파일을 Write·Edit로만 썼다.

- #7(세션 `2e039bc4`): Write 1번, Edit 3번. Bash로 쓴 적 없음.
- #18(세션 `e547cd96`): Write 2번, Edit 4번. Bash는 읽기(`cat`)에만 썼다.
- 단계 지시가 단계마다 들어왔다. 상태: 해결.

### 비유로 보기

| 비유 | 실제 |
| --- | --- |
| 직원 | AI 에이전트 |
| 업무일지 | `task.json` |
| 자동 지시서 기계 | 훅. 일지에 단계를 적으면 그 단계에서 할 일을 뽑아 준다 |
| 전용 펜 | Write·Edit 도구. 기계는 이 펜으로 쓴 것만 알아차린다 |

- 직원이 일지를 전용 펜이 아닌 아무 펜(Bash)으로 썼다. 기계가 못 알아채서 지시서가 안 나왔다.
- 업무 안내문에는 "일지를 쓴다"만 있었다. 회사 기본 규칙은 "짧은 메모는 아무 펜이나 써도 된다"였다. 직원은 꼼수를 부린 게 아니라 몰랐다.
- 그래서 경비를 세우지 않고 안내문에 "일지는 전용 펜으로 쓴다" 한 줄을 넣었다. 그래도 또 그러면 그때 경비를 세운다.

### 배운 점

뚫릴 수 있는 길을 전부 막으려 하면 장치가 끝없이 늘어난다. 실제로 일어난 일과 그 원인부터 봐야 한다. 몰라서 생긴 실수는 막기보다 알려 주는 게 맞다.

## 2. 백그라운드 서브에이전트를 기다리는 동안 Stop 게이트가 반복해서 막았다

**한 줄 요약:** 서브에이전트를 기다리는 동안 종료 차단이 반복되는 문제를 해결했다. Stop 입력의 `background_tasks`로 '작업 종료'와 '대기'를 구분했다. 참고한 원본 엔진(ai-bouncer)에도 같은 구멍이 있음을 코드에서 찾았다.

### 기술 설명

**배경: Stop 게이트와 반복 방지 규칙**

- `stop-gate.sh`는 Stop 훅이다. 에이전트가 턴을 끝내려 할 때만 돈다.
  - 작업 주인 세션이고 `stage`가 `done`이 아니면, 이유를 stderr로 내고 exit 2로 막는다(발표 슬라이드 14).
- 반복 방지는 ai-bouncer `hooks/stop.sh`의 `guarded_block`을 따른다.
  - `tool-count.sh`(PreToolUse, matcher `*`)는 주인 세션의 도구 호출 수를 `.harness/state/tool-seq`에 센다.
  - 막을 때 `stop-gate.json`에 `{key, seq, stage, streak}`를 적는다. key는 단계와 이유의 체크섬이고, seq는 그 시점의 도구 수다.
  - 재진입(`stop_hook_active: true`)했는데 key와 seq가 같으면 막지 않는다. 그 사이 도구를 하나도 쓰지 않았다는 뜻이고, 막아도 같은 답만 반복된다. ai-bouncer에서는 이런 반복이 54건 관찰됐고 최대 939회까지 갔다.
  - 같은 단계에서 10번(`HARNESS_MAX_CONTINUE`) 연속이면 더 막지 않고 사용자에게 묻게 한다.

**문제**

- IntervalTimer #8의 verify 단계에서 일어났다. 에이전트가 ios-reviewer 서브에이전트를 백그라운드로 띄우고, 결과를 기다리려고 턴을 끝냈다.
- Stop 게이트가 1분 사이 4번 막았다. 에이전트는 출력 파일을 확인하는 루프로 버텼고, 리뷰 결과가 온 뒤에야 정상으로 이어 갔다.
- 첫 차단(18:40:46)과 두 번째 차단(18:40:51) 사이에 메인 에이전트는 글만 썼고 도구를 쓰지 않았다. 그런데도 반복 방지 규칙이 걸리지 않았다.
- ReadSharp #218에서도 같은 모양으로 4번 막힌 적이 있다. 당시에는 한 번 관찰이라 보류했다.

**원인** (계층: State)

- 그 5초 사이 리뷰어 서브에이전트가 Bash를 2번 썼다(18:40:47·48, `subagents/agent-a78a57dd2408a6cdd.jsonl`).
- 서브에이전트의 도구 호출도 메인과 같은 `session_id`로 `tool-count.sh`에 들어온다. 그래서 `tool-seq`가 올라갔고, 게이트는 "도구를 썼다"로 보고 다시 막았다. 원인은 시각을 맞춰 보고 추정했다.
- 근본 원인: 게이트는 다음 둘을 구분하지 못한다.
  - 작업을 그만두려는 Stop
  - 백그라운드 작업을 기다리며 잠깐 쉬는 Stop
- ai-bouncer도 구조가 같다(코드를 읽어 확인했고, 돌려 보지는 않았다).
  - `hooks/pre-tool.sh`는 같은 세션의 모든 호출을 `.tool_seq`로 센다. `agent_id`를 따로 보지 않는다.
  - `hooks/stop.sh`는 `background_tasks`를 보지 않는다.
  - 이 규칙을 넣은 커밋 `6c6c90d`의 주석은 "백그라운드 작업이 끝나면 그 알림으로 턴이 다시 열리고, 그때 다시 판정한다"이다. 그런데 테스트 `21-no-ask-and-bg-wait.sh`는 기다리는 동안 도구 호출이 없는 경우만 다룬다.

**해결**

- `stop-gate.sh`가 Stop 입력의 `background_tasks`에서 `type == "subagent"`인 항목을 센다. 1개 이상이면 막지 않고 exit 0으로 끝낸다.
  - 위치는 주인 세션 확인과 `done` 확인 다음이다. 그래서 다른 세션이거나 이미 끝난 작업이면 원래대로 처리된다.
  - 차단 기록(`stop-gate.json`)은 건드리지 않는다.
  - 서브에이전트가 끝나면 그 알림으로 턴이 다시 열린다. 다음 Stop에서 게이트가 다시 판정한다.
- `tool-count.sh`는 그대로 둔다. 서브에이전트의 도구도 계속 센다.
- 셸(`shell`)·모니터(`monitor`)는 넣지 않는다. 개발 서버처럼 끝나지 않는 작업이 있으면, 일을 끝내지 않고 멈추는 우회로가 된다.
- 입력 필드의 근거
  - 설치된 Claude Code 2.1.317 실행 파일의 Stop 입력 스키마를 읽었다.
    - `background_tasks` 설명: "In-flight background work (running/pending + backgrounded)… Lets hooks distinguish 'session is done' from 'session is paused waiting for background work to wake it'. Empty array when nothing is in flight."
    - 항목 필드: `id`, `type`('shell'·'subagent'·'monitor'·'workflow'), `status`, `description`, `agent_type`.
  - 진행 중인 작업만 들어오므로 `status`는 보지 않는다.
- 검토하고 쓰지 않은 방법

| 방법 | 쓰지 않은 이유 |
| --- | --- |
| `tool-count.sh`에서 서브에이전트 호출(입력에 `agent_id`가 있는 호출)은 세지 않기 | `agent_id`를 잘못 가리면 메인 호출까지 빠진다. 그러면 두 번째 차단부터 항상 풀려, 일이 남았는데 끝내게 둔다. 포그라운드 서브에이전트는 메인이 기다리는 동안 Stop이 불리지 않아서 얻는 것도 없다 |
| 백그라운드 작업이 무엇이든 하나라도 있으면 막지 않기 | 셸·모니터가 끝나지 않는 경우의 우회로 |

- ai-bouncer와 다른 동작이다. 사용자에게 보고하고 정한 뒤 [ADR 0013](decisions/0013-stop-wait-subagent.md)에 남겼다.
- 테스트(`tests/stop-gate.test.sh`)에 5가지 경우를 추가했다.
  - 서브에이전트가 돌고 있으면 막지 않는다(0).
  - 이때 차단 기록을 남기지 않는다.
  - 배열이 비었으면 막는다(2).
  - 셸만 돌고 있으면 막는다(2).
  - `done`이면 서브에이전트와 상관없이 막지 않는다(0).
- 커밋: `fb60e65`
- 남겨 둔 것
  - 서브에이전트를 중간에 취소했을 때의 동작은 확인하지 않았다.
  - 취소되면 배열에서 빠지므로 다음 Stop에서 다시 막는다고 본다. 일을 끝내지 않고 빠져나가는 길은 없다.

**결과:** 2026-11-04 IntervalTimer #18(세션 `e547cd96`, plan 모드, 검사 unit-test·review)에서 확인했다.

- 실제 Stop 입력에 `background_tasks`가 들어온다. 서브에이전트가 없을 때는 `[]`, 리뷰어가 돌 때는 `type: "subagent"`, `status: "running"` 항목이 들어왔다.
- 00:41:54, verify 단계에서 리뷰어("Review force-update fix")가 도는 동안 Stop이 왔다. 게이트가 막지 않았고, 차단 기록(`stop-gate.json`)도 생기지 않았다.
- 리뷰가 끝나자 턴이 다시 열렸고, 에이전트가 이어서 finish까지 마쳤다. 작업 전체에서 차단은 0번이었다(#8은 같은 상황에서 4번).
- 상태: 해결.

### 비유로 보기

| 비유 | 실제 |
| --- | --- |
| 직원 | 메인 AI 에이전트 |
| 심부름꾼 | 서브에이전트(코드 리뷰어) |
| 문지기 | Stop 훅. 일이 안 끝났으면 직원이 퇴근(턴 종료)하지 못하게 막는다 |

- 문지기의 원래 규칙은 두 가지였다.
  1. 일이 안 끝났으면 퇴근을 막는다.
  2. 막은 뒤 직원이 아무 일도 안 하고 또 나가려 하면 보내 준다.
- 직원이 심부름꾼을 보내 놓고 기다리는 동안 잠깐 나가려 했다. 문지기는 심부름꾼이 한 일까지 직원이 한 일로 셌다. 그러고는 "일하고 있네, 못 나가"라며 계속 막았다.
- 그래서 일을 세는 방식은 두고, 문지기가 "지금 심부름 나간 사람이 있나?"만 보게 했다. 있으면 잠깐 보내 준다. 심부름꾼이 돌아오면 직원이 다시 불려 오고, 그때 다시 본다.
- 틀어 놓은 기계(백그라운드 셸·모니터)는 이유로 쳐 주지 않는다. 영영 안 끝날 수 있어서, 그걸 핑계로 퇴근하게 두면 안 된다.

### 배운 점

참고한 원본에서 규칙을 가져오면 구멍도 같이 따라온다. 쉽게 떠오른 해결책(서브에이전트 호출 빼기)이 더 큰 구멍을 낼 수도 있다. 그래서 판단에 필요한 정보(기다리는 중인가)를 직접 보는 쪽을 골랐다.

## 3. 문답: 기본 개념

### Bash가 뭐야?

에이전트가 터미널 명령을 실행할 때 쓰는 도구다. 사람이 터미널에 `ls`, `git status`를 치는 것과 같다.

에이전트가 파일을 고치는 방법은 두 가지다.

| 방법 | 예 | 하네스 훅이 아는가 |
|---|---|---|
| Write·Edit 도구 | "task.json을 이 내용으로 저장" | 안다. 훅이 걸려 단계 지시를 넣고, 검사를 돌리고, 작업 주인을 기록한다 |
| Bash 도구 | `cat > task.json <<'EOF' ... EOF` | 모른다. 훅이 Write·Edit에만 걸려 있다 |

### task 스킬은 뭐야?

작업을 시작할 때 에이전트가 읽는 안내서다(`plugin/skills/task/SKILL.md`). "이 버그 고쳐 줘"처럼 코드를 고치는 일을 시키면 에이전트가 먼저 이 문서를 연다.

1. 진행 중인 작업이 있는지 `task.json`을 읽는다.
2. 모드(plan/simple)와 검사를 사용자에게 묻는다.
3. `task.json`을 Write로 쓴다. 쓰는 순간 훅이 첫 단계 지시를 넣는다.
4. 그다음부터는 훅이 넣는 지시를 따른다.

### 리뷰(review 검사)는 코드 리뷰를 말하는 거야?

맞다. 플러그인에 들어 있는 `ios-reviewer` 서브에이전트가 이번에 바뀐 코드를 읽고 버그나 문제를 찾아 보고한다. 사람 대신 AI 리뷰어가 한 번 더 보는 단계다. 차단 항목이 나오면 메인 에이전트가 고친다.

## 4. 문답: 작업 흐름 (모드·단계·검사)

### 플랜은 에이전트가 무엇을 근거로 짜?

범위를 자동으로 정해 주는 장치는 없다. 에이전트가 아래 근거로 판단하고, 맞는지는 승인할 때 사람이 본다.

1. **이슈 본문**: 위치, 문제, 근거 코드, 고치는 방법 제안. 범위를 정하는 가장 큰 근거다.
2. **실제 코드**: 이슈가 가리키는 코드와 그 코드를 쓰는 곳을 읽고 영향 범위를 본다.
3. **위키 기록(`docs/wiki/`)**: plan 단계 지시가 `scripts/harness/wiki search`로 관련 정책·결정을 먼저 찾아 읽게 한다. 의도된 동작을 버그로 보고 고치는 일을 막는다.
4. **프로젝트 규칙**: `AGENTS.md`, `.claude/rules/`. 어느 모듈을 바꾸는지, 의존 방향을 지키는지 계획에 적게 되어 있다.
5. **고른 검사**: 확인 방법이 검사로 정해진다.

하네스가 강제하는 건 두 가지다.
- 계획에 바꿀 파일·바꾸는 방법·확인 방법을 담는다.
- 승인(ExitPlanMode) 전에는 코드를 고치지 않는다.

이슈가 고치는 방법을 여러 개 제안하면, 계획이 어느 쪽을 왜 골랐는지 승인할 때 확인한다.

### 계획 승인을 기다리는데 Stop 훅을 왜 넣어?

처음에는 승인을 기다려야 해서 Stop 훅을 빼려 했다. 그 뒤 발표대로 넣었다(슬라이드 14: 완료 단계가 아니면 멈추지 못하게 막는다).

승인 대기는 Plan 모드 승인 창 안에서 일어난다. 그래서 턴을 끝내지 않고 기다리고, Stop 훅과 부딪히지 않는다.

### "고칠 수 없는 실패"가 뭔데?

과장이었다. 정확히는 **이번 작업과 상관없는 곳에서 난 실패라서, 손대도 되는지 사람이 정해야 하는 실패**다. 예를 들면 불안정한 공통 e2e 흐름, main에 원래 있던 테스트 실패, 시뮬레이터가 없는 환경 문제가 있다.

이런 실패는 남겨 둘 게 아니라 고쳐야 한다. 그래서 Stop 훅을 빼는 이유가 되지 않는다.

### verify 단계에서는 뭐 해?

고른 검사를 지시대로 하나씩 돌리고, 실패하면 고친다.

- 검사에 `run`이 있으면 다음 단계로 넘어갈 때 훅이 직접 실행해 판정한다. 예: `passed unit-test`
- `passed`는 결과 파일(`.harness/out/<이름>.json`)이 통과로 기록되어 있고 그 뒤로 작업 트리가 바뀌지 않았는지 본다.
- review처럼 `run`이 없는 검사는 지시만 있고 훅이 확인하지 않는다.

### verify가 "두 가지 역할"이라는 게 뭐야?

역할이 두 개라는 뜻이 아니었다. 같은 이름이 단계(verify 단계)와 검사(verify 검사)에 함께 붙어 있었다. 헷갈려서 검사 이름을 발표·ai-bouncer에 맞춰 `unit-test`로 바꿨다. 이제 verify는 단계 이름뿐이다.

### unit-test를 고르면 테스트도 새로 쓰게 해?

아니다. 기존 테스트를 돌리고 통과할 때까지 고치는 것만 시킨다. `passed unit-test`도 결과가 통과인지만 보고, 새 테스트가 있는지는 보지 않는다.

### 그럼 테스트 케이스 작성은 하네스에 없어?

규칙은 있지만 강제하지 않는다.

- `.claude/rules/harness/testing.md`: 버그는 실패하는 테스트로 먼저 재현하고, Given-When-Then으로 쓰고, 테스트를 약화하거나 지우지 않는다.
- 이 규칙은 테스트 파일을 열 때만 로드된다. 그래서 테스트 파일을 한 번도 안 열면 못 볼 수 있다.
- "테스트 먼저 안 쓰면 코드 못 쓰게 막는 장치"는 로드맵의 "만들지 않는 것"에 있다. 발표 팀이 써 보고 걷어냈다.
- 꼭 받고 싶으면 계획을 승인할 때 "재현 테스트 추가"를 계획에 넣으라고 말한다.

## 5. 문답: 훅은 언제 무엇을 하나

### 훅은 언제 불려?

| 언제 | 훅 | 하는 일 |
|---|---|---|
| 에이전트가 `task.json`을 Write·Edit로 고칠 때 | `check-run.sh` | 다음 단계로 넘어가기 전에 고른 검사의 run을 돌린다. 실패하면 못 넘어간다 |
| 위와 같음 | `stage-context.sh` | 새 단계의 지시를 넣고, 작업 주인 세션을 기록한다 |
| 에이전트가 턴을 끝내려 할 때 | `stop-gate.sh` | `task.json`을 읽기만 한다. done이 아니면 못 끝내게 막는다 |
| 도구를 쓸 때마다 | `tool-count.sh` | 도구 호출 수를 센다. Stop 게이트가 반복 차단을 풀 때 쓴다 |
| 생성 파일·pbxproj를 고치려 할 때 | `protect-generated.sh` | 막는다 |

**턴을 끝낸다**는 에이전트가 말을 멈추고 사용자에게 차례를 넘기는 것이다. Stop 훅은 이 순간에만 불리고, 파일 편집과는 상관없다.

### 그러니까 task 상태를 바꿀 때 훅이 진짜 작업했는지 확인하는 거야?

맞다. 다만 막는 게 기본이 아니라 확인이 기본이다. 에이전트가 `stage`를 바꾸면 훅이 run을 돌려 보고, 통과하면 그대로 두고 실패할 때만 막는다. 에이전트의 말이 아니라 실행 결과로 판정한다(발표 슬라이드 29).

### 지금까지 ReadSharp·IntervalTimer에서 훅이 한 번도 안 돌았어? (Bash로 편집해서)

아니다. 세션 기록 6개를 확인했더니 단계를 바꿀 때는 거의 다 Write·Edit를 썼고 훅이 돌았다. Bash로 쓴 건 두 세션에서 작업을 시작할 때 한 번씩이고, 둘 다 에이전트가 곧바로 Write로 다시 저장했다.

### 에이전트가 JSON을 고칠 때 Bash를 쓰는 게 기본이야?

기본은 아니다. Claude Code 기본 지침은 Write·Edit를 우선한다. 그런데 auto 모드에서는 "작은 수정은 Bash로 해도 된다"는 안내가 붙는다. 그래서 auto 모드에서 Bash로 쓰는 일이 생겼다.

### Bash 말고 다른 걸로 고쳐도 안 뚫린다는 보장 있어?

보장은 없다. Bash 말고도 Write·Edit를 거치지 않는 경로가 있다.
- 경로를 변수에 숨기거나 스크립트 파일 안에서 쓰기
- Monitor 도구나 파일을 쓰는 MCP 도구
- 사람이나 다른 프로그램이 직접 고치기

하지만 실제로 본 두 번은 모두 평범한 Bash였고, 나머지는 일부러 돌아가야 생긴다. 그래서 "관찰된 실패만 막는다"는 원칙대로 task 스킬에 한 줄만 넣었다: "task.json은 Write로 쓴다. Bash로 쓰면 단계 지시가 들어오지 않는다." 다시 관찰되면 그때 훅을 만든다.

### 리뷰어를 기다리는 동안 Stop 게이트가 왜 계속 막았어?

1. 메인 에이전트가 리뷰를 서브에이전트에게 맡기고, 기다리는 동안 할 일이 없어 턴을 끝냈다. 쉬려던 것이다.
2. Stop 게이트는 stage가 verify라 막았다.
3. "막은 뒤 도구를 하나도 안 쓰고 다시 끝내려 하면 풀어 준다"는 규칙이 있다. 그런데 그 사이 리뷰어가 쓴 도구까지 같이 셌다.
4. 그래서 일한 것으로 보고 계속 막았다. 4번 반복됐다.

### 서브에이전트가 쓴 도구를 세지 않으면 위험하지 않아?

위험하다. 그래서 그 방법은 버렸다.
- 서브에이전트를 구분하는 표시(`agent_id`)가 메인 세션에도 붙는 경우가 있으면 메인 호출도 안 세게 된다. 그러면 게이트가 두 번째부터 항상 풀린다.
- 대신 도구 수는 그대로 세고, Stop 게이트가 "지금 돌고 있는 서브에이전트가 있나"만 본다(`background_tasks`).
  - 있으면 기다리는 중이라고 보고 막지 않는다.
  - 서브에이전트가 끝나면 턴이 다시 열리고, 그때 다시 판정한다.
- 셸·모니터는 끝나지 않을 수 있어서 넣지 않았다(ADR 0013).

2026-11-04 IntervalTimer #18에서 실제로 확인했다. verify 단계에서 리뷰어가 도는 동안 Stop이 왔고, 게이트가 막지 않았다.

### 서브에이전트를 중간에 취소하면 어떻게 돼?

게이트는 "돌고 있는" 서브에이전트만 본다. 취소된 뒤에는 원래대로 막는다. 그래서 일이 안 끝났는데 빠져나가는 경로는 없다. 최악의 경우는 메인이 사용자가 말을 걸 때까지 쉬는 것이다. 이 경우는 문제가 생기면 고치기로 했다.

### 훅이 늘어나면 작업이 많아지고 느려지는 거 아니야?

훅 하나는 호출마다 0.01~0.03초라 체감할 만큼 느려지지는 않는다. 그래도 관리할 것과 깨질 곳이 늘어난다. 그래서 두 문제를 고칠 때 새 훅을 만들지 않았다. 스킬에 한 줄을 넣고, 기존 Stop 게이트에 몇 줄을 더했다.

## 6. 문답: ai-bouncer와 비교

### ai-bouncer도 이렇게 되어 있어?

구조가 다르다. 훅이 확인하는 순간이 다르다.

| | 훅이 확인하는 때 | 단계를 바꾸는 쪽 |
|---|---|---|
| 우리 하네스(발표와 같음) | `task.json`을 고칠 때 + 끝내려 할 때 | 에이전트 |
| ai-bouncer | 끝내려 할 때(Stop) | 훅 |

- **우리**: 에이전트가 "다음 단계로 간다"며 `task.json`을 고칠 때 훅이 확인한다.
- **ai-bouncer**: 에이전트가 "다 했다"며 끝내려 할 때 훅이 확인하고, 단계도 훅이 넘긴다.

그래서 Bash로 상태 파일을 쓰는 문제는 우리 쪽에서만 생긴다. ai-bouncer는 에이전트가 상태 파일을 쓸 일이 없다.

### 그냥 ai-bouncer처럼 끝낼 때만 확인하면 더 깔끔하지 않아?

깔끔한 건 맞지만 지금 구조를 유지했다.
- Stop은 "일을 마쳤다"는 뜻이 아닐 때가 많다. 질문하거나 백그라운드 작업을 기다리려고 멈출 때도 Stop이 온다. 그때 단계가 잘못 넘어갈 수 있다(코드를 읽고 추론한 것이고, ai-bouncer에서 직접 돌려 보지는 않았다).
- 우리 쪽은 `stage`를 바꾸는 것이 "이 단계는 끝났다"는 분명한 신호다. 멈추는 것과 단계를 넘기는 것이 따로 간다.
- 발표 구조(슬라이드 14·27)와 같고, 바꾸려면 훅 3개와 스킬·문서를 다시 짜야 한다.

### 11월 2일에 승인 없이 단계가 넘어간 일은 우리 하네스에서 있었던 일이야?

아니다. 이 저장소에서 ai-bouncer를 켜고 작업하다 생긴 일이다. 그때 설정은 `bouncer init`이 만든 빈 설정이라 plan 단계에 확인할 run이 없었다. 이 일이 ai-bouncer를 함께 쓰지 않기로 한 이유가 됐다(ADR 0005).

### ai-bouncer도 리뷰어를 기다릴 때 같은 문제가 있어?

코드로 보면 있다. `pre-tool.sh`는 같은 세션이면 서브에이전트 호출도 다 세고, `stop.sh`는 `background_tasks`를 보지 않는다. 직접 돌려 보지는 않았다. 우리 반복 차단 규칙을 ai-bouncer에서 가져왔기 때문에 구멍도 같이 따라왔다.

### dev-bounce 규칙(`~/Code/.claude/CLAUDE.md`)을 지우면 다른 프로젝트에서 못 써?

쓸 수 있다. dev-bounce를 실제로 돌리는 스킬과 훅은 `~/.claude` 아래에 있다. 새 프로젝트를 열면 세션 시작 훅이 켤지도 묻는다. 지운 건 "모든 개발 작업 전에 dev-bounce부터 부르라"는 문구 하나다.
