# 0005. 여기어때 안드로이드 팀 발표의 기준으로 이후 후보를 다시 정하고, 워크플로 엔진은 함께 쓰지 않는다

- 상태: 채택
- 날짜: 2026-11-03

## 배경

- 여기어때 안드로이드 팀이 DroidKnights 2026에서 하네스를 v1에서 v2로 바꾼 과정을 발표했다. 요약은 [references.md](../references.md)의 "팀 적용 사례"에 있다.
- 이 레포의 원칙과 이미 맞는 점이 많다.
  - 결정적 검증 우선
  - 프로젝트마다 다른 사실은 설정 파일에
  - 강제 장치는 늦게
  - 필요 없어진 구성요소는 뺀다
- 이 레포에 없던 것은 세 가지다.
  - 작업마다 사람이 검사와 계획 여부를 고른다. 검사마다 `prompt`(시킬 일)와 `run`(했는지 확인) 두 개를 둔다.
  - 코드에 남지 않는 결정을 기록하고 다시 읽게 한다.
  - 컨벤션·화면·동작을 각각 도구로 판정한다.
- 발표 팀은 v1에서 넣었던 장치를 실험한 뒤 걷어냈다.
  - Phase·Step 분할: 웹 큰 작업에서 나눔 93.1%, 안 나눔 94.4%
  - 모든 작업에 같은 검사
  - 계획 여부를 AI가 고르기: 큰 작업 결함 비율이 simple 78%, plan 25%였고, 작업 크기는 AI도 미리 알기 어렵다
- 2026-11-02, 하네스 레포에 워크플로 엔진 ai-bouncer를 켜고 작업을 시작했다.
  - 엔진은 계획 승인도 구현도 없는 상태에서 응답이 끝날 때마다 plan → implement → verify → finalize로 단계를 넘겼다.
  - 그리고 "모든 단계 완료"로 작업을 닫았다.
  - 작업 흐름을 맡는 장치가 둘이면 서로 다른 상태를 본다.

## 결정

| 항목 | 결정 |
|---|---|
| 원칙 | principles.md에 11(검사는 작업마다 사람이 고른다), 12(코드에 남지 않는 결정은 기록한다)를 넣는다. 결정적 검증 설명에 "완료 판정은 실행 결과로"를 넣는다 |
| 후보 10 | 동작 검증(Maestro와 팀 작성 규칙, 회귀 태그, 전후 영상)을 먼저 하고, 화면 검증(`#Preview` 스냅샷 + Figma 수치 비교)은 그다음에 한다. 픽셀 비교는 쓰지 않는다 |
| 후보 11 | 컨벤션은 AI가 규칙 초안만 뽑고, 검사는 SwiftLint·SwiftFormat이 한다. 결과는 `passed`를 담은 파일로 남긴다 |
| 후보 12 | 작업 흐름을 하네스 안에 만든다. 검사 목록은 `.harness/checks.json`(`name`·`prompt`·`run`)에 둔다 |
| 후보 13 | 여전히 조건부다(원칙 2). 켤 때 run은 결과 파일과 작업 트리 해시만 확인한다. (2026-11-03 ADR 0012: 조건을 걷고 발표대로 켰다. 작업 트리 해시는 넣지 않았다) |
| 후보 19 (신규) | 기술 기록(`kind: fact`)과 결정 기록(`kind: rule`). 마무리 때 쓰고 시작할 때 찾는다. 처음에는 프로젝트 안 `docs/wiki/`로 한다 |
| 설정 파일 | `project.json`에는 사실만 둔다. "무엇을 검사할지"는 정책이라 `checks.json`으로 나눈다 |
| 만들지 않는 것 | Phase·Step 분할, 테스트 먼저 강제 훅, 모든 작업에 같은 검사, AI가 모드 고르기 |
| 워크플로 엔진 | ai-bouncer 같은 외부 워크플로 엔진은 하네스 레포와 시험장에서 쓰지 않는다 |

- 후보 번호는 바꾸지 않는다. README·ADR 0004·principles가 후보 14·16·17을 번호로 참조한다.

## 결과

- 좋아지는 점
  - 이후 후보의 내용이 실제 운영 사례로 구체화된다. 발표 팀이 실험으로 걷어낸 장치를 처음부터 피할 수 있다.
  - 작업 흐름을 맡는 장치가 하나라 단계 상태가 엇갈리지 않는다.
- 비용
  - 작업 흐름(후보 12)을 직접 만들어야 한다.
  - 발표는 안드로이드 사례다. iOS에는 Roborazzi 같은 JVM 렌더러가 없어서 스냅샷에 시뮬레이터가 필요하다. SwiftUI는 레이아웃 수치를 코드에서 정적으로 뽑기도 어렵다. 그래서 화면 검증은 뒤로 미뤘다.
- 확인 방법
  - 각 후보를 시험장(ReadSharp)에서 실행해 확인한다.
  - 후보 13을 켤지는 단위 9 운영 기록으로 정한다.
