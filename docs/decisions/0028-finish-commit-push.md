# 0028. 마무리 단계에서 커밋하고 push하며, Stop 훅이 이를 확인한다

- 상태: 채택 (2026-11-08)
- 관련: ADR 0007(작업 흐름), ADR 0027(Stop 훅이 단계를 넘긴다), `plugin/hooks/stop-gate.sh`, `plugin/hooks/stage-text.jq`, `template/AGENTS.md`

## 배경

- 발표 v2의 마무리 단계는 "이번에 정한 정책 정리"다(슬라이드 39·46). 커밋은 이 단계에 없다.
- 발표 v1은 Phase마다 커밋했다(슬라이드 17). 문제로 꼽은 것은 "CLAUDE.md에 커밋까지 하라고 적어 둬도 커밋을 빠뜨린다"였다(슬라이드 5).
- ai-bouncer의 finalize는 개별 `git add`, 커밋, push를 하고, 무관한 WIP는 그대로 둔다(`engine/default.yaml`). run은 없어서 빠뜨려도 작업이 닫힌다.
- 지금까지 이 하네스의 finish는 보고만 하고, 커밋·push는 사용자가 따로 시켰다. template AGENTS.md도 "사용자가 요청하거나 승인한 뒤에 한다"였다.
- 사용자 결정(2026-11-08): "마무리 단계에서 커밋 푸시하자 우리도. 귀찮아 죽겠다". 훅이 확인하고, 기본 브랜치면 새 브랜치를 만들어 push한다.

## 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 지시 | finish 지시: 위키 기록 → 개별 `git add` → 커밋 → push → 작업 보고. 비밀 정보와 무관한 변경은 그대로 둔다. PR은 만들지 않는다 | ai-bouncer finalize와 같다. 위키도 커밋에 들어가게 위키 다음에 한다 |
| 브랜치 | 기본 브랜치(`origin/HEAD`, 없으면 main·master·develop·development)면 커밋 전에 새 브랜치를 만든다 | 사용자 git 규칙. 기본 브랜치에 바로 push하지 않는다 |
| 확인 | Stop 훅이 finish를 닫기 전에 본다. 시작 때 없던 변경이 남았는지, 커밋이 있으면 기본 브랜치가 아닌 브랜치에서 upstream까지 push됐는지 | 지시만으로는 빠뜨린다(슬라이드 5). 확인은 git 상태만 보는 결정적 판정이다 |
| 무관한 WIP | 새 작업을 시작할 때 바뀌어 있던 파일을 `.harness/state/task.wip`에 적고, 그 파일은 남아 있어도 막지 않는다 | 무관한 WIP는 커밋하지 않는다(ai-bouncer). PetCycle처럼 다른 작업이 섞인 작업 트리가 있다 |
| 확인하지 않는 경우 | 시작 커밋(`task.base`)이 없거나 git 저장소가 아님. 원격이 없으면 push는 보지 않는다 | 판단할 수 없으면 막지 않는다(stop-gate.sh의 원칙) |
| 기록 | `task.history`의 advance·blocked에 `commit`·`push` 결과를 run처럼 남긴다 | 보고의 단계 기록 표가 읽는다 |

## 발표·ai-bouncer와 다른 점

- 발표와 다르다: v2 마무리에는 커밋이 없다. 사용자가 정했다. 발표가 지적한 "커밋 지시를 까먹는다"는 훅의 확인으로 막는다.
- ai-bouncer와 다르다: finalize는 지시만 한다. 우리는 Stop 훅이 커밋·push를 확인하고, 기본 브랜치면 새 브랜치를 만들게 한다.

## 결과

- 작업 하나가 끝나면 커밋·push까지 된다. 사용자는 PR과 머지만 정한다.
- 시작 전부터 바뀌어 있던 파일을 이 작업에서 더 고치면, 커밋하지 않아도 훅은 모른다. 지시와 보고(건의)에 맡긴다.
- 기본 브랜치에 이미 커밋했으면 훅은 막고 사용자에게 알리게 한다. 10번 연속이면 사용자에게 넘긴다(ADR 0012).
