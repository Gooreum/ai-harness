# 0001. 하네스를 다섯 계층으로 나누고, 산출물을 템플릿과 플러그인으로 나눠 배포한다

- 상태: 채택
- 날짜: 2026-10-01

## 배경

- 지침, 스크립트, 훅, 리뷰 같은 구성요소를 어디에 두고 어떤 기준으로 추가할지 정하려면 공통 언어가 필요하다.
- 하네스를 여러 프로젝트에 재사용하려면, 프로젝트마다 달라지는 것과 공통인 것을 나눠야 한다.
- 배포 방식에는 플랫폼 제약이 있다.
  - Claude Code 플러그인은 항상 로드되는 지침(CLAUDE.md)을 담을 수 없다.
  - 프로젝트 밖으로 symlink한 경로 규칙은 로드되지 않는다.
- 검증 스크립트는 에이전트뿐 아니라 사람과 CI도 실행해야 한다.

## 결정

### 1. 계층을 다섯 개로 나눈다

| 계층 | 하는 일 |
|---|---|
| Context | 행동 전에 알려준다 |
| Execution | 에이전트가 일을 하는 손이다 |
| Validation | 결과가 맞는지 판정한다 (결정적 / 추론적) |
| Enforcement | 모델 판단과 상관없이 막는다 |
| State | 위 계층이 함께 쓰는 데이터 |

### 2. 산출물을 아래 위치에 둔다

| 위치 | 담는 것 | 이유 |
|---|---|---|
| `template/` → 각 프로젝트에 복사 | AGENTS.md, 경로 규칙, 프로젝트 설정 파일 양식, 프로젝트 안에서 실행하는 스크립트, settings.json | 항상 로드되는 지침과 경로 규칙은 프로젝트 안에 있어야 하고, 스크립트는 사람·CI도 써야 한다 |
| `plugin/` → 플러그인으로 배포 | 스킬, 훅, 서브에이전트 | 중앙에서 고치면 모든 프로젝트에 반영된다 |
| 저장소 `scripts/` | 하네스를 설치·관리하는 도구(detect, dev-install, 이후 init/sync) | 프로젝트 밖에서 실행된다 |
| 각 프로젝트에만 | 프로젝트 설정 값, 프로젝트 고유 규칙 | 프로젝트마다 다르다 |

### 3. 구성요소는 막는 실패나 위험을 설명할 수 있을 때만 추가한다

- 강제 장치는 처음에는 위험하거나 되돌리기 어려운 행동을 막는 것만 넣는다.
- 나머지 강제 장치는 실패가 관찰된 뒤에 넣는다.

## 결과

- 좋아지는 점
  - 새 구성요소를 어디에 둘지, 넣을지 말지 판단할 기준이 생긴다.
  - 지침·스크립트(템플릿)는 프로젝트마다 버전이 고정되고, 스킬·훅(플러그인)은 중앙에서 갱신된다.
- 비용
  - 템플릿 파일이 프로젝트마다 복사되므로 갱신 도구가 필요하다(후보 14 init/sync).
  - 그 전까지는 dev-install로 수동 동기화한다.
- 다시 검토할 때
  - 단위 9(파일럿 운영)를 마친 뒤
  - Claude Code가 플러그인으로 항상 로드되는 지침을 지원하게 될 때
