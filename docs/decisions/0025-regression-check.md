# 0025. 회귀 묶음은 고를 수 있는 검사 하나로 둔다

- 상태: 채택 (2026-11-07)
- 관련: ADR 0009(Maestro 시나리오), ADR 0024(하네스는 플랫폼을 모른다), 로드맵 단위 32, `template/scripts/harness/setup`, `docs/checks.md`

## 배경

- 회귀 묶음(`tags: [regression]`이 붙은 시나리오 모음)을 언제 돌릴지 정하지 않았다. `docs/checks.md`는 "작업 검사에 넣지 않고 배포 전·리팩터링 뒤에 돌린다"고만 적었고, 누가 언제 부르는지는 비어 있었다.
- 발표 슬라이드 86: 회귀 묶음은 "배포 전 새 버전 통합 검증 때"와 "리팩터링 후"에 한 번에 돌린다. 노트 81은 파일로 남긴 시나리오를 "CI에 붙여 회귀 테스트로도 쓸 수 있다"고 했다. 어디에 거는지는 말하지 않는다.
- 발표 슬라이드 24·30: 검사는 config에 모아 두고 작업을 시작할 때 사람이 고른다. ai-bouncer에는 배포·회귀를 따로 다루는 코드가 없다.

## 결정

- 회귀 묶음 전체는 `checks.json`의 검사 하나(`regression`)로 둔다. 배포 준비나 리팩터링 작업을 시작할 때 사용자가 고르면, 검증 단계에서 `record regression <명령>`으로 돌리고 `passed regression`으로 판정한다.
- 일반 작업의 `e2e` 검사에는 넣지 않는다. 이번 기능과 영향 받는 흐름만 돈다(슬라이드 23: 매번 전부 돌면 오래 걸린다).
- 하네스가 따로 돌리는 때는 만들지 않는다.
  - 훅: 단계 훅이 이미 고른 검사만 돌린다. 회귀만 따로 걸 이유가 없다.
  - CI·git 훅: 저장소마다 CI가 다르다. 하네스가 알면 ADR 0024와 어긋난다. CI에 붙일지는 프로젝트가 정한다.
- 회귀 묶음 명령도 하네스가 모른다. setup이 회귀 묶음이 있는지 묻고 그 명령으로 검사를 쓴다.

## 결과

- 시험장 ReadSharp·IntervalTimer의 `checks.json`에 `regression`(`scripts/ios/e2e --tag regression`)을 넣었다.
