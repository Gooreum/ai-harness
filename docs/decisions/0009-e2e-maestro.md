# 0009. 동작 확인은 Maestro 시나리오 파일과 e2e 스크립트로 한다

- 상태: 채택
- 날짜: 2026-11-03

## 배경

- 발표의 동작 검증(슬라이드 79~, 전사 "동작 검증 — Maestro E2E")
  - 대화로 시키면 그때 한 번으로 끝난다. 시나리오를 파일로 남기면 다시 돌릴 수 있고 회귀 테스트가 된다.
  - Appium 대신 Maestro를 골랐다: YAML이라 작성·검토가 쉽고, 화면이 준비될 때까지 알아서 기다리고, MCP와 CLI를 다 쓸 수 있다.
  - 같은 요청에도 AI마다 시나리오 품질이 달랐다(문구로만 찾기, 계정 하드코딩, 개인 경로, 화면만 뜨면 성공). 그래서 팀 작성 규칙을 만들었다.
  - `tags: [regression]` 묶음을 배포 전·리팩터링 뒤에 돌리고, QA 티켓은 수정 전후 영상을 MR에 붙인다.
  - 서버 응답 조작(프록시 MCP)과 행동 로그 판정도 했다.
- 이 Mac에는 Maestro 2.11이 이미 설치돼 있다. ReadSharp에는 accessibilityIdentifier가 하나도 없다.

## 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 도구 | Maestro CLI | 발표와 같다. 시뮬레이터에서 바로 돌고 결과를 JUnit으로 남긴다 |
| 위치 | 프로젝트 `.maestro/`, 공통 흐름은 `.maestro/common/` | Maestro 관례. 폴더를 넘기면 바로 아래 파일만 돌아 공통 흐름이 따로 돌지 않는다 |
| 작성 규칙 | template 규칙 `rules/harness/maestro.md`(`.maestro/**`를 열 때 읽힘) | 발표의 팀 규칙. 스킬이나 생성 도구 없이 경로 규칙으로 시작한다 |
| 실행 | `scripts/harness/e2e`: 빌드 → 설치 → `maestro test` → `.harness/out/e2e.json` | 앱 ID·기기·결과 해석을 스크립트가 맡아 에이전트가 명령을 조립하지 않는다(설계 원칙) |
| 앱 ID | `appId: ${APP_ID}`, 스크립트가 `app.bundleId`를 넣는다 | 프로젝트마다 다른 사실은 설정 파일에 둔다 |
| 회귀 | `--tag regression` | 발표와 같다 |
| 영상 | `--record`: `xcrun simctl io recordVideo`로 화면 전체를 녹화 | Maestro 녹화 기능 없이 기본 도구로 된다 |
| 검사 목록 | 프로젝트 `checks.json`에 `e2e` 검사를 둔다(`run`은 `e2e.json`의 `passed`) | 작업마다 사람이 고른다(원칙 11) |

## 결과

- ReadSharp에 회귀 시나리오 2개를 만들었다(프로필 빈 상태, 설정 진입). 처음 만든 시나리오는 두 번 실패했고, 실패 스크린샷으로 원인을 찾아 고쳤다.
  - 온보딩이 실행 직후 늦게 떠서 "보이면 누르기" 조건이 먼저 지나갔다. 데이터를 지우면 늘 뜨므로 뜰 때까지 기다려 누르게 했다.
  - "AI 모델" 항목은 이 빌드에서 보이지 않았다. 늘 보이는 항목으로 확인하게 했다.
- id가 없어 화면 문구로 찾는다. 앱에 accessibilityIdentifier를 다는 것은 앱 작업이라 따로 한다.
- 남은 것: 서버 응답 조작, 행동 로그 판정, 화면 검증(`#Preview` 스냅샷 + Figma 수치 비교). 로드맵 후보 10에 남긴다.
