# 0033. 계획에서 e2e가 필요하다고 정하면 시나리오를 쓰고, 돌릴지는 사람이 정한다

- 상태: 채택 (2026-11-28)
- 관련: ADR 0009(Maestro 시나리오), ADR 0024(플랫폼을 모른다), ADR 0030(계획 확인), `template/scripts/harness/e2e-plan`, `template/scripts/harness/e2e-criteria.md`, `plugin/hooks/stage-text.sh`

## 배경

- ADR 0030은 e2e 시나리오가 필요한지 계획에서 정하는 장치를 프로젝트에 맡겼다. PetCycle은 판단 기준을 위키에 두고 `scripts/e2e-planned.sh`로 확인했다.
  - `plan`은 계획서의 판단 줄 형식만 본다.
  - 시나리오를 썼는지와 돌렸는지는 `verify`가 본다. 이 확인은 e2e-ios 검사의 run에만 붙어 있었다.
- 빈틈: 검사는 작업을 시작할 때 고르고, e2e 판단은 그 뒤 계획에서 나온다. e2e 검사를 고르지 않은 작업에서 계획이 "필요"로 나오면 `verify`가 돌지 않는다. 그러면 계획한 시나리오를 쓰지 않아도 작업이 끝난다. e2e-android에는 `verify`가 아예 없었다.
- 확인한 사실(2026-11-28): PetCycle의 이 구성은 머지되지 않은 `chore/light-theme-sky-blue` 브랜치(bd837a3)에만 있었다. `development`에는 없었다.
- 사용자 결정(2026-11-28)
  - "e2e는 시간이 많이 걸리는 작업이기 때문에 반드시 사람이 결정해야 한다."
  - "e2e를 선택하지 않더라도, 계획에 e2e가 필요하다 판단이 되면 e2e 시나리오를 작성하도록 해라."
  - "펫사이클만의 문제가 아니라 하네스 자체의 문제이니 하네스를 수정하도록 한다."
  - 돌리지 않은 시나리오는 보고에 적고, 표시를 남겨 다음에 e2e를 고른 작업에서 함께 돌리게 한다.
- 발표: e2e 검사의 prompt가 시나리오를 만들게 하고, run이 통과를 확인한다(슬라이드 29). 돌릴 검사는 작업마다 사람이 고른다(슬라이드 30). 작성한 시나리오는 처음부터 끝까지 돌려 통과한 것만 저장한다(슬라이드 84 노트). 계획에서 e2e를 판단하는 장치는 발표에 없다.
- ai-bouncer: e2e를 다루는 코드가 없다. 단계마다 `prompt_file`과 `run`을 둔다(`engine/default.yaml`, `hooks/stop.sh`).

## 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 어디에 둘지 | 확인 스크립트(`scripts/harness/e2e-plan`)와 판단 기준(`scripts/harness/e2e-criteria.md`)을 template에 둔다. 켜는 것은 프로젝트 설정이다 | 어느 프로젝트에서나 같은 빈틈이 생긴다. 훅 코드는 e2e를 모른다. 프로젝트가 위키 확인(ADR 0032)처럼 설정으로 이 확인을 켠다 |
| 하네스가 아는 것 | 시나리오 폴더(`project.json`의 `e2e.scenarios`)와 e2e 검사 표시(`checks.json` 검사의 `"e2e": true`)만 본다 | e2e 도구와 실행 명령은 프로젝트가 갖는다(ADR 0024). 두 값만 있으면 이 확인은 iOS·안드로이드·웹에서 똑같이 동작한다 |
| 판단 기준 | 일반 기준 N1~N4·U1~U4를 하네스 문서로 둔다. 무엇이 핵심 흐름인지(N3)는 프로젝트 위키에 둔다 | PetCycle 기준 가운데 프로젝트마다 다른 것은 핵심 흐름뿐이었다 |
| 기준을 읽게 하기 | `stages.plan.prompt_file`에 `scripts/harness/e2e-criteria.md`를 둔다. `prompt_file`은 경로 하나나 배열을 받는다 | 프로젝트가 이미 자기 기준 문서를 두었어도 함께 넣을 수 있게 한다 |
| 계획 확인 | `e2e-plan plan`: 판단 줄, 시나리오 줄, 필요면 시작점·동작·확인. e2e 검사를 고르지 않았고 판단이 필요·기존 수정이면 `- e2e 실행: 안 함` 줄을 요구한다 | 사람이 승인 창에서 "시나리오는 쓰지만 돌리지 않는다"를 보고 정하게 한다. 돌리자고 하면 에이전트가 그 검사를 더한다(task 스킬) |
| 시나리오 작성 확인 | `stages.implement.run`의 `e2e-plan written`: 계획한 시나리오 파일이 있고 이번 작업에서 쓰거나 고쳤는지 본다. e2e 검사를 골랐는지와 관계없다 | 사용자 결정. 시나리오는 implement에서 쓴다(ADR 0030) |
| 실행 확인 | e2e 검사 run 끝의 `e2e-plan ran <검사>`: 그 검사의 실행 명령에 계획한 시나리오와 아직 돌리지 않은 시나리오(또는 그 폴더)가 있는지 본다. e2e 검사를 고른 작업에서만 돈다 | 돌릴지는 사람이 정한다. 이 확인은 `"e2e": true`가 붙은 검사마다 돈다. 그래서 e2e-android도 e2e-ios와 같은 확인을 받는다 |
| 돌리지 않은 시나리오 | `written`이 e2e 검사를 고르지 않은 작업의 시나리오를 `.harness/e2e-unrun`에 남긴다. 이 파일은 커밋한다. `ran`이 통과하면 돌린 시나리오를 목록에서 뺀다. 시나리오 파일을 지웠으면 그 줄도 뺀다 | 사용자 결정. 다음에 e2e를 고른 작업에서 빠뜨리지 않게 한다. `.harness/` 아래라 `passed`의 최신 확인에 걸리지 않는다 |
| 이미 설치한 프로젝트 | doctor가 빠진 설정을 알리고, setup은 e2e 검사가 있으면 묻지 않고 켠다 | `checks.json`과 `project.json`은 프로젝트 파일이라 sync가 고치지 않는다 |

## 발표·ai-bouncer와 다른 점

- 발표와 다르다: 발표 팀은 작성한 시나리오를 끝까지 돌려 통과한 것만 저장한다(슬라이드 84). e2e 검사를 고르지 않은 작업에서는 돌리지 않은 시나리오가 커밋된다. 사용자가 실행 시간 때문에 실행은 사람이 정하게 했다. 하네스는 돌리지 않은 시나리오를 `.harness/e2e-unrun`에 남긴다. 다음에 e2e를 고른 작업이 그 시나리오를 돌려 통과하면 목록에서 뺀다.
- 발표에 없는 것: 계획에서 e2e 필요 여부를 정하는 장치는 ADR 0030부터 있었다. 이번에는 그 장치를 프로젝트에서 하네스로 옮겼다.
- ai-bouncer와 같다: 단계 확인은 `stages.<단계>.run`과 `prompt_file`로 한다.
- 막지 않는 것: 에이전트가 `.harness/e2e-unrun`을 고쳐 목록을 지우거나, 계획서에 필요 없는 시나리오를 적는 것은 막지 않는다. 그런 실패가 아직 관찰되지 않았다(docs/principles.md의 강제 장치 원칙). 목록은 커밋에 남아 사람이 본다.

## 결과

- 설정을 켠 프로젝트에서는 계획에서 e2e가 필요하다고 정하면, e2e를 고르지 않았어도 implement를 넘기기 전에 시나리오를 써야 한다.
- e2e를 고른 작업에서는 에이전트가 계획한 시나리오와 쌓인 미실행 시나리오를 함께 돌려야 하네스가 verify를 넘긴다.
- simple 모드는 계획서가 없어 계획한 시나리오 확인을 건너뛴다. 다만 e2e를 고르면 미실행 시나리오는 돌려야 한다.
- PetCycle은 `e2e-planned.sh` 대신 이 설정을 쓰면 된다. 옮기는 일은 PetCycle 쪽 작업으로 따로 한다.
