# Git

## 승인

- 커밋, push, PR 생성·머지는 사용자가 요청하거나 승인한 뒤에 한다. 커밋 전에는 메시지와 대상 파일을 먼저 보여준다.
- 사용자가 명시적으로 요청하지 않으면 파괴적인 명령을 쓰지 않는다: `push --force`, `reset --hard`, `clean -fd`, `checkout -- .` / `restore .`, `branch -D`, 이미 push된 브랜치의 rebase.
- `--no-verify` 등으로 훅을 우회하지 않는다. 훅이 막으면 원인을 해결한다.

## 커밋

- 커밋 하나에는 논리적인 변경 하나만 담는다. 관련 없는 포매팅·리팩터를 섞지 않는다.
- 커밋 메시지는 프로젝트의 기존 컨벤션(언어, prefix)을 따른다. 모르면 `git log`로 확인한다. 제목에는 무엇을, 본문에는 왜를 쓴다.
- 커밋 전에 빌드와 관련 테스트가 통과한 상태인지 확인한다.
- `git add -A` / `git add .` 대신 파일을 지정해 스테이징하고, `git diff --staged`로 대상을 확인한다.
- 비밀 정보(API 키, 인증서, 프로비저닝 프로파일, `.env`)와 생성 산출물(DerivedData, `xcuserdata`, 생성 도구가 만든 프로젝트 파일)을 커밋하지 않는다.

## 브랜치·PR

- 프로젝트 규칙이 따로 없으면 기본 브랜치에 직접 커밋하지 않고 작업 브랜치를 만든다. 브랜치 이름은 프로젝트 관례를 따른다(예: `feature/<주제>`, `fix/<주제>`).
- PR 본문에는 변경 요약과 검증 방법·결과를 쓴다.
- 충돌을 해결할 때 상대 쪽 변경을 임의로 버리지 않는다. 의도가 불분명하면 확인한다.
- 여러 워크트리를 쓰는 환경에서는 `git worktree list`로 현재 위치를 확인하고, `git -C <경로>`로 명령 대상을 명시한다.
